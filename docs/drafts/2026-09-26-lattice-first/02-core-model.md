- Требование переносимости: модель должна раскладываться в Anchor Modeling без миграции смысла, но без множества
  файлов — атрибутов мало, они не накапливаются (Q55).
- Maintainer (2026-09-26): назвать механизм правильно и сделать частью LATTICE?
- Сверка с LATTICE (2026-09-26): почти всё уже есть — snapshot / `based_on` (D8.3), `version` и `content_hash`

## Идея

### 1. Две формы — всё остальное типы и правила

| Форма | Поля | Что это |
|---|---|---|
| **объект** | `id`, `type` (+ `version` у сущностей) | всё, у чего есть identity: норма, группа, вопрос, оценка, тип, правило ([04-terms](04-terms.md) T1) |
| **posit** | `id`, `of: [{ref, role}]`, `value`, `at` | факт о связи объектов со значением на момент; не объект (§45), `id` — для ссылок assertions |

Объекты делятся на **сущности** (identity стабильна, есть история: `<context>/<name>`, T2) и **значения** (identity =
содержимое, неизменны: snapshot, T3) — различие entity / value object. Тип и правило — тоже объекты, но их носитель —
файл реестра под ревью, а не ledger (T8, T9).

Атрибут, членство, балл, assertion — всё posit'ы; различаются только набором ролей:

| Факт | `of` (роли) | `value` |
|---|---|---|
| создание сущности | `[{X, "object"}]` | `{ "type": "answer", "domain": "lifecycle" }` |
| атрибут | `[{X, "label"}]` | `"Как устроен цикл WARRANT"` |
| членство | `[{G, "group"}, {M, "member"}]` | `true` — вошёл, `false` — вышел |
| snapshot | `[{S, "snapshot"}]` | `{ "type", "domain", "members": ["<id>@<version>", …] }` |
| мера | `[{A, "measurement"}, {M, "candidate"}]` | `0.83` |
| assertion | `[{P, "posit"}, {W, "asserter"}]` | `0.5` (надёжность, −1…1) |

### 2. Ledger — журнал утверждений

- Один файл `ledger.jsonl`, только дописывание, одна форма строки (Q55, T14). Запись не мутирует: отмена —
  новый posit (`false` для членства) или assertion с отрицательной надёжностью.
- Текущее состояние (последние значения, составы, snapshot'ы, статусы, доверие) — **вычисляемый индекс**; руками не
  правится, пересобирается из ledger (как projection LATTICE, LD-T-07).
- Нормы, документы, units в ledger не пишутся: живут в своих источниках, ledger ссылается на них `id@version`.
- Правила проверяются дважды (Q56): `hard` — при записи (ссылка на существующий объект, роль из реестра типа, форма
  значения); `soft` — lint (размер группы > 7, раскачка членства).

### 3. Группа и snapshot

| | Группа (сущность, T21) | Snapshot (значение, T24) |
|---|---|---|
| identity | `<context>/<PREFIX>-<DOM>-<ULID>` ([03](03-classification-ids.md)) | `SN-<hash>`: sha256 канонического JSON `{type, domain, members}` (Q54) |
| зерно | (type, domain, потребность) | (type, domain, [член@версия]) |
| меняется | состав — posit'ы членства; атрибуты | никогда |
| кто ссылается | mapping вопросов, вердикты | оценки, вердикты — «на каком составе» (как `based_on`) |

- **Составная группа** (Q44): член — другая группа; snapshot родителя — дерево Меркла от snapshot'ов детей;
  изменение листа поднимается вверх само; родитель следует за калибровкой ребёнка; граф без циклов; выдача —
  `flatten`.
- **Статус snapshot'а** — вычисляется: `fresh` (все версии совпали), `stale` (изменились версии членов — список),
  `broken` (член не найден). Версии даёт порт `source`: до LATTICE — хэш записи объекта (Q21′), после — `version`.

### 4. Доверие — вычисляется из assertions по осям LATTICE

| Ось | Значение | Когда (правила реестра, пороги — Q38) |
|---|---|---|
| `grounding` | `inferred` | только assertion создавшего LLM-агента |
| | `observed` | ≥ 2 согласных assertions из разных сессий |
| | `declared` | есть assertion maintainer'а |
| `epistemic_state` | `settled` | нет противоречащих assertions |
| | `contested` | есть «+» и «−» об одном факте; раскачка — 2 цикла |
| | `unresolved` | assertions есть, но их суммы не хватает для решения |

Доверие вычисляется у каждого факта (членство, mapping), статус группы — по её фактам. Это заменяет счётчики Q37–Q38
одним механизмом (Q49).

### 5. Операции ядра (Q42)

| Операция | Вход → выход |
|---|---|
| `make(type, domain, members)` | → snapshot (значение) |
| `status(snapshot, source)` | → `fresh` · `stale[changed]` · `broken[missing]` |
| `evolve(group, {add, remove}, asserter)` | → posit'ы членства + assertions |
| `flatten(snapshot)` | → листья без дублей |
| `append(posit)` / `read(query)` | через порт хранилища; `append` проверяет правила `hard` |

Ядро не знает о вопросах, Jev, доменах поиска: это потребитель (kb-search) и его реестр типов.

### 6. Раскладка в Anchor Modeling (Q55)

| Ledger | AM |
|---|---|
| различные `ref` сущностей | anchors |
| posit с одной ролью | attribute: таблица `<type>_<role>`, `at` — время историзации |
| posit с ≥ 2 ролями | tie: таблица по набору ролей, историзуемая |
| значения из закрытых реестров (type, domain, статусы) | knots |
| assertion | assertion Transitional Modeling (posit о posit'е + reliability) |

Переход — механическая projection одного файла в таблицы, смысл не меняется. PostgreSQL / AM — только если понадобится
(LD-T-03).

### 7. Место в SEF — часть LATTICE (предложение этой записи)

| Часть | Слой LATTICE | Основание |
|---|---|---|
| identity, версия, ссылка `id@version` | `kernel` (§3.1) | уже там |
| snapshot | `kernel` / read model (D8.3) | уже там: набор версий |
| ledger, posit, assertion | хранилище history и provenance (LD-T-01, LD-T-02) | новое: единый журнал и надёжность |
| реестр, правила | `meta` (формат) + context registries (содержание) (§6, §12) | уже там |
| группа | тип в context (`lexicon/answer` и др.), механика членства — общая | новое как общий тип |
| доверие | оси `grounding`, `epistemic_state` (§19–20) | уже там; новое — вычисление из assertions |

Порядок (Q10, Q12): реализуется в LATTICE после фазы 4 WARRANT — в vertical slice входит то, что нужно ему (identity,
версии, history, provenance, `grounding`); assertions, группы и доверие — следующим шагом по потребности kb-search
(LD-B-06). До этого kb-search не реализует ledger у себя: кэш остаётся как есть, рефакторинг навыка (Q8) — только
разделение на модули.

## Вопросы для grilling

1. **Сделать механизм частью LATTICE** (п. 7): ledger и assertions — в хранилище и `kernel` LATTICE, группа — общий
   тип, kb-search — первый потребитель? Рекомендация: да; до slice ничего из этого в навыке не реализуется, чтобы
   не делать дважды.
2. **Конфликт SSOT.** LATTICE §41: «история — projection, не второй SSOT»; LD-T-01: SSOT разделён по осям. У нас
   ledger — SSOT, состояние — projection (event sourcing, как AM). Рекомендация: вопрос в grilling реестра LD-*
   первым после стека; до решения в этом черновике не менять.
3. **Assertions и proposals.** В LATTICE мутации идут через proposal, authority — у WARRANT (LD-*, integrations/02).
   Калибровка по вердиктам — мутация по правилу без человека. Рекомендация: assertions агентов — наблюдения
   (`evidence/observation`), не мутации; изменение состава — mutation по правилу реестра, авторизованному заранее
   policy WARRANT (одно решение на тип, не на каждую калибровку). Решать в grilling реестра.
4. **Где лежит ledger до LATTICE** (группы калибруют агенты всех worktree): локально в `.kb-search/` основного
   checkout (как кэш, Q22) — или не заводить до LATTICE (вопрос 1)? Рекомендация: не заводить (вопрос 1).
5. **Доверие — две оси LATTICE** (п. 4) вместо одной шкалы `inferred` / `observed` / `declared` / `contested`
   (Q33, Q38). Рекомендация: да — это уточнение формы принятого, пороги те же.
6. **Имя** — ledger (журнал утверждений)? Рекомендация: да ([04-terms](04-terms.md) вопрос 1).
