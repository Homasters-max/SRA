# Поиск по коду через граф

Код WARRANT (`packages/**`, `scripts/**` — `.ts`, `.js`) проиндексирован графом: узлы — функции, типы, файлы;
рёбра — кто кого вызывает и импортирует. Запрос к графу стоит сотни токенов и не пропускает связи; чтение исходников
целиком стоит тысячи и пропускает. Документы (`docs/**`, `openspec/**`, `*.md`) и данные (`*.json`) граф не
индексирует — их читай и ищи обычными средствами.

Инструмент — `cs`: `node scripts/dev/cs.js <команда>` из корня worktree (из подкаталога —
`node "$(git rev-parse --show-toplevel)/scripts/dev/cs.js" <команда>`). Индекс строится и обновляется сам, после
правок ничего запускать не нужно.

## Правила (обязательные)

1. **Код ищешь только через `cs`.** Не использовать для кода: инструменты Grep и Glob по `packages/`, `scripts/`,
   `*.ts`; `grep -r`, `rg`, `find` по коду; `graft` напрямую.
2. **Код читаешь только диапазонами.** Сначала `cs skeleton <файл>` (или `file:line` из ответа `cs`), затем Read с
   `offset`/`limit` (или `sed -n a,bp`) — только нужные строки. Файл кода целиком (Read без `offset`/`limit`, `cat`)
   не читать, даже короткий: у короткого диапазон `1..N` из skeleton.
3. **Перед изменением сигнатуры, переименованием, удалением, сменой поведения экспорта** — `cs callers <символ> -d 2`;
   перед правкой нескольких файлов (рефакторинг, перенос в порты) — `cs callers <символ> -d all`. Каждое место из
   ответа — учесть в правке или явно отметить, почему не затронуто.
4. **Один вызов — один ответ.** Выбери команду по таблице ниже, действуй по ответу. Не переспрашивай тот же вопрос
   другими словами: слабый ответ `ask` — переключись на `grep` / `skeleton` / `callers`.
5. **Не обрезай вывод** (`| head`, `| tail`): он уже ограничен и сообщает, что отброшено.
6. **`cs` вернул код 2 или 3** — не обходить: код 2 — поправь команду; код 3 — остановись и сообщи в отчёте.
   Пусто после двух разных команд `cs` по одному вопросу (например, `grep` с ослабленным шаблоном и `ask`) — тогда
   можно обычный поиск по этому вопросу, с пометкой в отчёте.

## Команды

| Задача | Команда |
|---|---|
| Где в коде поведение X (место неизвестно) | `cs ask "<где X>" --source` — топ совпадений с кодом (`--in <путь>`, `-n N`) |
| Все вхождения символа или литерала | `cs grep "<короткое имя>"` — по символам; не нашёл — ослабь шаблон (голое имя, без сигнатуры), `-i`, `--fixed` |
| API файла | `cs skeleton <файл>` — сигнатуры и строки |
| Кто вызывает / что сломается | `cs callers <символ> -d 2`; от чего зависит — `--direction out`; весь связный кусок — `-d all` |
| Незнакомая область | `cs map` — один раз, дальше по названным узлам |

## Сценарии

| Ты… | Путь |
|---|---|
| Знаешь символ, который меняешь | `cs grep "<символ>"` → правка по `file:line`; сигнатура меняется — сначала `callers -d 2` |
| Не знаешь, где это | `cs ask "<поведение>" --source` → `skeleton` нужного файла → Read диапазона |
| Переносишь вызовы за порт (`spawn`, `git`, `openspec`) | `cs grep "spawnSync"` (все места) → `cs callers <функция> -d all` → правки по списку |
| Разбираешь падение теста | `cs ask "<симптом>" --source` → `callers` подозреваемого |
| Пишешь тест на функцию | `cs skeleton <файл>` + `cs callers <функция>` (как её вызывают сейчас) |

## Отчёт

Раздел «Поиск по коду» в отчёте о задаче: какими командами нашёл ключевые места (2–3 примера), где ответ `cs` был
неверным или неполным и к чему это привело (или «нет»), где пришлось искать обычными средствами и почему.
