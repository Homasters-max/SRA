# 04 — ревью реализации на соответствие spec и разбор красного CI

## Проблема

**Ревью.**
- Ревью фазы 3 (2026-09-23, R-1…R-16) делалось вручную уже после merge, по пяти вопросам maintainer'а, и нашло
  настоящие дефекты нормы и кода. Например: R-1 — `transition MERGED` принимал любой commit-предок; R-6 — `--ref` не
  сверялся с attestation CI; R-7 — kind без gate закрывался любой записью. Исправления пришлось вести отдельной веткой
  `fix/phase-3-review`.
- Встроенный навык `code-review` ищет баги в diff, но не сверяет код с REQ/SCN delta specs, решениями I-N и ADR.
- Gate `adversarial-review` (продукт, фаза 4, producer через `codex exec`, D-5) пока снимается waivers WAV-2026-002/004/006/008.
- SCN-теги в тестах есть (68 файлов тестов) — покрытие SCN можно вычислить.

**CI.**
- Два дефекта первой фазы проявились только на Linux (I-100 — путь через 8.3-имя или symlink обнулял diff, `scope-valid`
  ложно `PASS`; I-101 — внешний `dirname` в обёртке теста). Разбор шёл вручную по логам.
- CI — матрица ubuntu + windows (P-9), job `evidence` на impl-PR с ожидаемым `WAIT` по `human-approval` (его легко
  принять за сбой). На машине maintainer'а есть WSL и Docker.

## Идея

**`review-impl`** — ревью impl-PR до merge, в отдельном субагенте (не автор кода). Вход: diff impl-PR, delta specs,
design.md (I-N), ADR из proposal.

| Шаг | Что проверяет |
|---|---|
| каждый REQ/SCN delta | есть код и тест с тегом SCN (скрипт: SCN из delta минус SCN в тестах) |
| каждое I-N | реализовано так, как записано |
| объём | файлы вне задач tasks.md — это расползание объёма (см. 05, «минимальная правка») |
| нормы ADR | границы модулей (что не покрывает `architecture.test`), топология, доверие |
| вопросы maintainer'а | если заданы, как пять вопросов ревью фазы 3 |

Находки — метками важности из агента `code-reviewer`: 🔴 блокер / 🟡 предложение / 💭 мелочь. Блокер правится в той же
ветке до merge, остальное уходит в `backlog.md` строкой R-N.

**`ci-triage`** — CI красный:
1. `gh pr checks` → `gh run view <id> --log-failed`.
2. Классификация:
   - платформа — пути, регистр, 8.3-имена, CRLF, spawn, внешние утилиты;
   - таймаут или нестабильный тест;
   - настоящий дефект;
   - ожидаемое (`WAIT` job `evidence`).
3. Воспроизведение Linux-сбоя: WSL или `docker run node:22`.
4. Исправление с тестом уровня по ADR-0025.

## Вопросы для grilling

❓ **R1 — Место ревью в жизненном цикле.** Варианты:
- (a) после `VERIFYING`, до merge impl-PR — шаг `change-impl-pr` (02);
- (b) после merge, как в фазе 3;
- (c) после каждой группы.

➡️ (a). Правка до merge дешевле отдельной ветки исправлений. Группы уже проверяет `/group-done`.

❓ **R2 — Кто ревьюит.** Варианты:
- (a) субагент `general-purpose` с промптом навыка;
- (b) тип агента `.claude/agents/reviewer.md` без `Write` и `Edit` (как ADR-0014 п. 3 для продукта);
- (c) Codex (`codex exec`) — другая модель, как продуктовый `adversarial-review`.

➡️ (b) сейчас: минимум прав без новой зависимости. (c) — вопрос фазы 4, вместе с producer'ом gate.

❓ **R3 — Может ли dev-ревью стать producer'ом gate `adversarial-review`.** Тогда waivers для него не нужны. Но это
продуктовая норма (06, 07-skills, D-5), а evidence от субагента Claude — это attestation `none`.

➡️ Нет, это разные вещи. Записать строкой в `backlog.md` → grilling фазы 4: сравнить результаты dev-ревью и
`adversarial-review` на одном Change.

❓ **R4 — Покрытие SCN скриптом.** `scripts/dev/scn-coverage.js`: SCN из delta specs Change против тегов в тестах.
Варианты:
- (a) dev-скрипт для ревью;
- (b) сразу продуктовый check (`scn-covered`) в pack `core-sdd`.

➡️ (a) сейчас. (b) — кандидат фазы 5 (`bdd-tdd`, где SCN — центральное понятие).

❓ **R5 — `ci-triage` навыком или справочником.** Варианты:
- (a) отдельный навык;
- (b) справочник `git-land/ci.md` к навыку PR (01);
- (c) раздел `packages/cli/CLAUDE.md` «платформенные ловушки».

➡️ (b) + (c): шаги разбора — справочник навыка PR, список ловушек (I-100, I-101 и следующие) — во вложенном
`CLAUDE.md`, где пишется код.

❓ **R6 — Воспроизведение Linux-сбоя локально.** WSL или Docker (`node:22` + openspec 1.13.1). Нужна одна команда
`npm run test:linux` в dev-скриптах?

➡️ Да, через Docker: образ воспроизводим, WSL у всех разный. Дорогое — только по требованию.
