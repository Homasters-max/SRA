# SEF — платформа тёмной фабрики разработки (design)

- **Дата:** 2026-09-17 · **Статус:** proposed, **rev 3 (2026-09-22)** — rev 3: приложение E; разделы §1–§15 согласованы владельцем по секциям в сессии
  2026-09-17 (rev 1); rev 2 — усиления по ревью `docs/engineering/audit-verification/Q-sef-platform-review-2026-09-17.md`

  этого файла и бюллетеня `decisions/sef-2026-09-17`.
- **Автор:** Claude Opus 5 по заданию владельца «проанализировать и доработать план фабрики с учётом Beads и Gas Town:
  упростить, унифицировать, взять готовую основу, не потеряв расширяемость».

  `soma.*`.

## 0. Почему пересборка

- **Факт исполнения rev 4.** fac0-01…05 закрыты: `tools/agentexec` (1225 LOC + 1133 LOC тестов), AVL и SA переведены на
  него. Это заняло ≈ 21 ч, ≈ 76 коммитов и ≈ 100 решений контроллера (R-14…R-116); большая часть — противоречия внутри
  брифов с полным кодом. Осталось 38 задач, ≈ 12,8 тыс. строк брифов, ≈ 133 новых файла, 10 конфигов, ≈ 21 схема, 3 FSM
  с CAS. Узкое место — церемония процесса и объём своего кода, а не рантайм.
- **Новая рамка владельца** (§1.1): независимый продукт, Ubuntu 24.04, 4–8 параллельных агентов, ACP, подписки,
  готовые основы, метрики и аудит.
- **Исследования** (приложение B): ни одна готовая система не закрывает требования целиком. Gas Town/Gas City, Beads,
  Archon, Bernstein, OpenHands SDK не годятся как основа, но дают проверенные паттерны. Готовые слои — Docker, ACP-адаптеры,
  DBOS, DuckDB, git — закрывают бóльшую часть инфраструктуры. Своё — тонкое ядро доверия.
- **Проба Linux** (§14.3): тесты SOMA на Ubuntu 24.04 — 3077 passed, 12 failed, 2 errors, 18 skipped за 130 с (`-n 8`);
  4 класса падений, из них 2 платформенных.

## 2. Продукт и границы

### 2.1 SEF

- Отдельный репозиторий `sef` (Python 3.12, Ubuntu 24.04, Docker), пакет `sef`, CLI `sef`. Диспетчер — только Linux;
  CLI стола работает и на Windows как тонкий клиент **control-API** диспетчера (`127.0.0.1:<port>`, локальный токен;
  §4.2, D-S21). MCP-сервер стола и публичный HTTP API — roadmap поверх того же `app`.
- **Проект** = git-репозиторий + пакет `.sef/` в нём: pipeline, гейты, зоны, роли → профили движков, промпты и скиллы ролей,
  образ контейнера, интеграции, политика (§6.3). Пакет версионируется вместе с кодом проекта.
- **Экземпляр SEF** — конфиг вне репозиториев: проекты (URL хаба, рабочая область), слоты и профили движков, лимиты
  ресурсов, хранилища (DBOS, журнал, evidence), срок хранения.
- SEF обслуживает несколько проектов одним экземпляром; первые два — сам `sef` и SOMA.

### 2.2 SOMA как проект

- Пакет SOMA (`.sef/` в репозитории SOMA): гейты `pytest -n 8`, `tests/architecture`, `scripts/eks/check.py`, smoke CLI
  на эфемерном DWH; зоны из `contracts/architecture.json`; core-зона; промпты с правилами SOMA.
- Компоненты SOMA подключаются к SEF гейтами и узлами пакета: EKS `check` — сразу; SA replay, AVL — roadmap (§13).
- SOMA использует компонент SEF `sef.engines` для запусков AVL и SA (единственная реализация запуска агентов) — **только
  через публичный, версионированный API `sef.engines`**; другие `sef.*` SOMA не импортирует (тест границы в
  `contracts/architecture.json` SOMA). SOMA не знает о DBOS и внутренностях SEF.
- SEF запускает SOMA как чёрный ящик: гейты и узлы пакета — `python -m soma …` (argv), не импорт `soma.*`. SOMA остаётся
  authority своей предметной области (DV-метаданные, каталог); SEF её семантику не дублирует.
- Стоп-правило ADR-028 сохраняется: Work над `src/soma/**` — срез S5, после приёмки R5 или по решению владельца.

### 2.3 Вне SEF

| Вне SEF                                                                                            | Почему                                                                  |
| -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Продуктовые треки SOMA: Reference DWH, Knowledge Pack, Memory Plane, облачный UI DSH, оператор DSH | продукт, не сборочная линия                                             |
| SA и AVL как системы                                                                               | остаются системами SOMA; к SEF подключаются гейтами                     |
| Портфель, спрос, приоритеты                                                                        | решает человек                                                          |
| Декомпозиция и дизайн агентом без человека                                                         | стадии «намерение → дизайн → план → approve» — стол (Claude + владелец) |

### 2.4 Самоприменение

SEF разрабатывает свой репозиторий своим же пакетом. Попытку судят SEF и пакет из `base` или релиза, а не из worktree
(INV-9). Ядро SEF, `.sef/**` и политика — core-зона, посадка только вручную.

## 3. Модель работы

### 3.1 Роли и ответственность

| Ответственность | Владелец | Claude (стол, интерактивно с владельцем) | SEF (детерминированно) | Codex / OpenCode (headless) |
|---|---|---|---|---|
| Намерение, приоритеты, бюджеты | решает | помогает сформулировать | — | — |
| Спека, ADR, план | утверждает | пишет | проверяет форму | — |
| Задачи с контрактом | `sef work approve` | пишет задачи и контракты | `validate`, `contract_hash` | — |
| Запуск в работу | approve = разрешение | вызывает `sef run` по поручению | допуск по ready, ресурсам, квоте | — |
| Реализация и repair | — | — | песочница, worktree, события | исполнитель |
| Проверка | — | — | гейты на чистом checkout | — |
| Ревью | политика по риску | стол ревью | пакет ревью, независимость | авторевью другим семейством |
| Посадка | ручная по политике | рекомендует | очередь, `push --ff-only` | — |
| Вопросы и эскалации | решает | анализирует, готовит ответ | блокирует задачу, пишет во входящие | задаёт вопрос |
| Остаток и находки | приоритизирует | разбирает `proposed` | фиксирует задачами | сообщает |
| Улучшение фабрики | утверждает | анализ метрик → задача-улучшение | метрики, отчёты | исполняет как обычную задачу |

Claude используется только интерактивно с владельцем (R8). `claude -p` в рантайме SEF не запускается; адаптер
`claude_cli` спит (AVL и SA в SOMA, явный API-профиль).

### 3.2 Политика: В1 и путь в В2

| Зона × риск | Ревью | Посадка | Запуск |
|---|---|---|---|
| core (ядро SEF, `.sef/**`, protected-пути, core-зона проекта) | стол, вердикт только `owner` | вручную | после подтверждения стола |
| обычная × trivial/small | авторевью другим семейством + гейты | до набора trust ceiling — вручную; после — авто | авто |
| обычная × normal/complex | стол; авторевью как вход | вручную | авто |

- **Пол риска (детерминирован, `policy.risk_floor`):** объявленный столом `risk` — нижняя оценка, не истина. Пересечение
  `impact` с core-зоной → `core`; с `protected[]` пакета (§6.3) → не ниже `normal`; после harvest фактический diff
  (число файлов, строк, затронутые зоны — пороги в политике) пересчитывает класс; **фактическое попадание diff в
  `protected[]` поднимает класс не ниже `normal` и минимального актора вердикта до `owner` независимо от заявленного
  риска** (заявленный риск — только вход допуска, authority — производный). Класс только повышается (событие
  `risk.escalated`), после чего политика ревью и посадки перерезолвится.

- **В2** (только обычная зона): normal/complex — два независимых авторевью и автопосадка по trust ceiling; стол — выборочный
  аудит и разбор инцидентов. Переход — изменение `.sef/policy.yaml` владельцем (событие `policy.changed`).
- **Отзыв автономии:** escape (§9.2) откатывает класс в ручной режим и замораживает его автопосадку до решения владельца
  (INV-16).
- **Trust ceiling** считается по классу `зона × риск × конфигурация` (движок, модель, версия пакета и политики); смена
  конфигурации сбрасывает счётчик (K6).

### 3.3 Стол

| Команда                                                                                                  | Что делает                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `sef inbox`                                                                                              | вопросы агентов, эскалации, ревью, ручные посадки, алерты квоты и авторизации — с приоритетом и возрастом                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `sef review next` / `sef review submit <id> --verdict APPROVED\|CHANGES_REQUESTED\|BLOCKED [--as owner]` | пакет ревью → вердикт с находками; `CHANGES_REQUESTED` → repair-попытка. Вердикт несёт `actor{kind: owner\|desk}`: Claude в скилле готовит вердикт как `desk`; `--as owner` — явное действие владельца в его терминале. Минимальный актор по классу — политика (core/complex — только `owner`), иначе P1 нарушен. **Механизм:** `--as owner` принимается только при подтверждении с реального TTY (чтение с консоли, не stdin; у Bash Claude Code TTY нет) и с owner-токеном control-API, который хранится в OS-keyring, не в env и не в файлах репозитория; без этого `--as owner`, набранный Claude в том же терминале, неотличим от владельца |
| `sef decide <id> --answer …`                                                                             | ответ на вопрос; ответ попадает в контекст следующей попытки                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `sef land <work>`                                                                                        | ручная посадка по политике                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `sef stop [--project\|--class\|--landing\|--all]` / `sef resume`                                         | мгновенная пауза запуска и/или посадки (очереди DBOS + флаг политики); `--landing` — снятие stop-the-line (INV-19)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `sef doctor`                                                                                             | согласованность DBOS ↔ журнал ↔ хаб ↔ контейнеры и слоты; версия workflows; сироты; `--fix` для безопасных случаев                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

Скиллы стола (Claude Code): `sef-design` (спека → задачи с контрактом и acceptance-тестами до approve), `sef-review`
(пакеты ревью; коммит попытки — из хаба, `refs/sef/attempts/<id>`), `sef-analyze` (отчёты и метрики →
задачи-улучшения). Стол не редактирует задачи в состоянии «в работе/на ревью» — `sef work validate` предупреждает по
статусу из control-API (иначе конфликты с посадкой, §5 3).

### 3.4 Независимость ревью

Вычисляется SEF из семейств профилей, а не заявляется агентом: `family` — семейства исполнителя и ревьюера различны
(Codex `openai` ↔ стол `anthropic`, OpenCode с GLM `zhipu`, с DeepSeek `deepseek`); `context_only` — одно семейство, чистый
контекст без транскрипта. Допустимость `context_only` по классам — данные политики.

## 4. Архитектура рантайма

### 4.1 Модули `sef` и швы

| Модуль | Ответственность | Шов (основа сейчас → roadmap) |
|---|---|---|
| `app` | сервисный слой сценариев: `work`, `run`, `review`, `decide`, `land`, `revert`, `stop`, `status`, `metrics`, `audit`, `doctor`; **control-API** (локальный HTTP на loopback, токен) — единственный вход стола в состояние диспетчера | все интерфейсы — через `app` → MCP-сервер для стола, публичный HTTP API, веб-UI |
| `cli` | CLI `sef`: на Linux — над `app`; на Windows (стол) — клиент control-API; одна кодовая база, режим по конфигу | тонкая обёртка над `app` |
| `work` | задачи-файлы, контракт, approval (в т. ч. blob-sha acceptance-тестов), ready-фронт, пересечение scope, резервирование scope, **context pack** попытки (недоверенные фрагменты помечены) | интерфейс хранилища задач → внешние трекеры, экспорт Backlog.md |
| `flow` | workflows и очереди DBOS; **единственный `import dbos`**; жизненный цикл попытки зашит в коде: `prepare → execute → harvest → verify → review → evaluate → land` (DSL узлов — roadmap) | Temporal — замена одного модуля |
| `engines` | адаптеры `acp`, `claude_cli` (спящий), `fake`; профили; аттестация оплаты; классы отказов; сигналы квоты; стоимость | новый ACP-агент — профиль; API-профиль — флаг |
| `sandbox` | два бэкенда явно: **агент** (сейчас Docker-контейнер; кандидат — Docker Sandboxes, SP-12) и **гейты** (Docker, `--network none`, CPU-токены); образ, монтирования, egress, пользователь, лимиты. Docker для гейтов ≠ обязательно песочница агента | `run(spec) -> handle` → microVM, удалённый раннер |
| `gitops` | worktree, harvest на хосте, коммит с трейлерами, rebase, посадка **(единственный merge/push в master)**, revert | batch/bisect посадки |
| `verify` | гейты (восстановление acceptance-тестов по blob-sha перед запуском), harvest-правила и reconcile (в т. ч. `judge_edit` по `protected[]`, `injection_suspect`), пакет ревью, `evaluate` (чистая функция), детектор escapes, cron-гейт `master` | узлы `security`, `drift` |
| `policy` | резолвер: зона × риск × конфигурация → режимы; `risk_floor`; минимальный актор вердикта; независимость; trust ladder; бюджеты; backpressure стола | В2 и автономия по зонам — данными |
| `journal` | журнал событий: один писатель, только дописывается, версия схемы, вычистка секретов | экспорт OpenTelemetry, загрузка в DWH SOMA |
| `metrics` | SQL-проекции журнала и git (DuckDB), отчёты, трасса аудита | evals, A/B, абляция |
| `pack` | загрузка пакета и политики проекта, схемы; пакет описывает возможности, ограничения, protected-пути, движки, гейты и настройки проекта — **не workflow** | плагины через entry points |

Правило модулей: новый модуль `sef.*` заводится только вместе с инвариантом, который он делает проверяемым AST-тестом
(так у `flow`, `engines`, `gitops`, `journal`, `policy`); дальше не дробить. Модуль — граница контроля, не фреймворк.

### 4.2 Процессы

- **Диспетчер `sef`** — один процесс на экземпляр в Linux-контейнере; DBOS: SQLite локально, Postgres на VPS.
  Контейнеры попыток и гейтов запускает через docker socket; сокет и учётки хаба есть **только** у диспетчера (INV-6).
- **Control-API** (D-S21): диспетчер слушает `127.0.0.1:<port>` (порт публикуется Docker только на loopback хоста),
  доступ — локальный токен из конфига экземпляра; все команды стола (`inbox`, `review`, `decide`, `land`, `stop`,
  `status`, `audit`) — вызовы `app` через него. Без него стол на Windows не видит ни DBOS, ни журнал (SQLite в volume
  с Windows недоступен). Артефакты для ревью стол берёт из хаба (`refs/sef/attempts/<id>`, §4.3), не из volume.
- **Модель угроз диспетчера (рамка; окончательная форма — после SP-12).** Диспетчер с docker socket имеет полномочия
  уровня хоста — это trusted control plane, единственная доверенная граница между столом и песочницами; его код —
  core-зона (INV-9). Rootless/выделенный хост песочниц — roadmap, S1 не усложняется. Если SP-12 принимает Docker
  Sandboxes, «docker socket только у диспетчера» становится «`/dev/kvm` и `sbx` только у диспетчера» (INV-6, SP-2).
- **Версия workflows.** `application_version` DBOS задаётся явно = версия пакета `sef`; DBOS восстанавливает только
  workflows своей версии, поэтому **обновление диспетчера** = `sef stop --all` → drain (терминальные состояния или
  таймаут → `aborted`) → замена образа → `sef resume`. Патруль помечает workflows чужой версии и не даёт им висеть
  молча (INV-15).
- **Журнал и evidence** — named volume экземпляра (`var/sef/journal`, `var/sef/attempts`), срок хранения по конфигу.

### 4.3 Git-топология: хаб

Bare-репозиторий на проект (хаб) — единственная точка истины `master`:

- рабочая копия владельца (Windows, стол Claude): pull/push спек, задач, approval;
- рабочая область фабрики (Linux volume): fetch, worktree попыток (на хосте, для harvest и коммита), посадка
  `push --ff-only`;
- **коммиты попыток** runner публикует в хаб под `refs/sef/attempts/<attempt_id>` (не ветки, не `master`): стол
  делает `git fetch` и ревьюит в IDE; INV-1 сохраняется — пишет только runner, `master` меняет только `gitops.land`;
  refs **неизменяемы** (без force-update; попытка → новый ref), убирает их патруль по сроку хранения evidence;
- позже хаб — на VPS или GitHub (смена URL в конфиге экземпляра).

Хаб не делит рабочее дерево между Windows и Linux (CRLF, скорость bind mount, блокировки) и отделяет посадку фабрики от
коммитов стола. Размещение хаба (bare на `D:` или volume + git daemon) — спайк SP-1 в S0. Правка `CLAUDE.md`: столу
разрешены `git pull --ff-only` и `git push` в локальный хаб (§14.4).

### 4.4 Контейнеры

| | Контейнер попытки | Контейнер гейтов |
|---|---|---|
| Образ | образ пакета проекта (Ubuntu 24.04, тулчейн проекта, закреплённые версии движков) | тот же образ |
| Код | **рабочая копия попытки**: экспорт `base_commit` (`git archive`) + одноразовый локальный репозиторий (`git init`, один коммит «base», без remotes, без учёток, `user.name = sef-attempt`) — агенту нужен `git status`/`git diff`, Codex без репозитория ограничивает режимы; локальная история при harvest отбрасывается. | Лимиты | CPU, RAM, wall time из профиля и бюджета | CPU-токены гейта |

Эталон egress — firewall devcontainer Claude Code; реализация (прокси или iptables) выбирается спайком под Rust (codex),
Node (codex-acp) и Bun (opencode). **Docker Sandboxes (`sbx`) — кандидат в бэкенд агента (SP-12, D-S29):** по данным
владельца (проверяются спайком) — microVM со своим ядром, docker-демоном и сетевым стеком, egress deny-by-default через
прокси на хосте, учётки инжектятся заголовками в прокси и в VM не попадают, workspace `mountless`/`clone`/`direct`,
требует Ubuntu 24.04+ и KVM. Если проходит — закрывает §4.4 egress и roadmap «брокер учёток» готовым (SP-3 — кандидат
на снятие). До прохождения SP-12: S1 = текущий Docker-бэкенд; после — решение владельца, S1-дефолт или поздний бэкенд.

### 4.5 Ресурсы и допуск

| Очередь DBOS | Параллельность | Назначение |
|---|---|---|
| `agents:<слот>` | 1 на слот; число слотов движка — конфиг экземпляра | исполнители; пауза до сброса квоты; резерв под ревью |
| `review:<профиль>` | конфиг | авторевью |
| `gates` | сумма CPU-токенов (конфиг, например 16 из 18 ядер); у гейта своя стоимость | гейты попыток и интеграции |
| `landing` | 1 | посадка строго по одной |

**Допуск задачи** (детерминирован, INV-17): зависимости `blocks` закрыты; `impact.write` не пересекается с задачами в
работе и с **резервами scope**; WIP (задачи от `prepared` до посадки) ≤ предела (конфиг; по умолчанию 2 × число
слотов); у движка есть слот и квота; **backpressure стола** — открытых элементов входящих ≤ `inbox_wip` (политика),
иначе задачи классов, требующих стола, не допускаются (очередь ревью не должна расти быстрее, чем стол её разбирает).

**Резервирование scope (против голодания):** задача, ждущая допуска дольше `reserve_after` (политика) или с
`priority` выше порога, резервирует свой `impact.write`: новые пересекающиеся задачи не допускаются, пока она не
стартует. Резерв — событие `scope.reserved`, видно в `sef status`.

## 5. Путь задачи (В1)

0. **Стол.** Claude и владелец пишут задачи с контрактом (§6.2): acceptance-тесты (**закоммичены в хаб до approve** в
   `.sef/acceptance/pending/<task>/` — вне обхода pytest проекта, иначе красные тесты на `master` уронят cron-гейт и
   включат stop-the-line (INV-19); красные на `base_commit` — TDD стола; `gitops.land` переносит каталог в
   `.sef/acceptance/active/<task>/` тем же коммитом — путь и `conftest` в `.sef/acceptance/` не меняются, проверено то
   же, что посажено; cron-гейт `master` = `pytest .sef/acceptance/active`, каталог и есть индекс), бюджет,
   стоп-условия, non-goals. `sef work validate` (схема, пол риска,
   существование blob'ов тестов, статусы) → `sef work approve`: снимок approval с blob-sha тестов коммитится в хаб.
1. **Допуск.** Workflow `work` синхронизирует рабочую область, вычисляет ready-фронт, применяет правила допуска (§4.5) и
   ставит задачу в очередь `agents:<слот>`.
2. **Workflow `task`:**
   - a) *Подготовка:* `attempt_id` (ULID); worktree на хосте от текущего `master` хаба (фиксируется
     `manifest.base_commit`); рабочая копия попытки — экспорт + одноразовый локальный git (§4.4); context pack
     (контракт из снимка, бриф, находки прошлых попыток и ревью, ответы стола; текст агента помечен недоверенным;
     `context_pack_sha` — в manifest, сам pack — evidence); execution manifest (§6.2). Событие `attempt.prepared`.
     Repair-попытка стартует от коммита предыдущей попытки (`parent_attempt`, тот же `base_commit`); если `master`
     ушёл — это новая попытка, не repair.
   - b) *Исполнение:* контейнер попытки; аттестация оплаты **и репозиторных конфигов движка** до первого вызова модели
     (§7.3); фактическая модель — на каждом ходу; результат `sef/result/1`: `done | abstain | blocked | scope_exceeded |
     needs_decision`, непроверенные допущения, остаток. Форма шагов DBOS: `start` идемпотентен по метке `attempt_id`
     (контейнер с меткой уже есть → не создавать), затем durable-цикл коротких `poll` (`DBOS.sleep`), затем `collect`;
     отмена (`sef stop`) — на границе `poll`. Так INV-14 — следствие формы, а не обещание.
     **Slot → Session → Attempt:** slot — ёмкость и вход движка (§7.4); attempt — логическое исполнение (контейнер +
     рабочая копия + manifest); session — процесс ACP внутри попытки. Падение адаптера/сессии → **рестарт сессии в той
     же попытке** (не новая попытка): событие `session.restarted{n, worktree_sha}` фиксирует sha рабочего дерева на
     момент рестарта; рестарт стартует с уже изменённой рабочей копии, поэтому воспроизведение попытки = `base_commit`
     + цепочка сессий из журнала; лимит рестартов — профиль; токены рестартов — в бюджет той же попытки; рестарт
     невозможен после начала harvest и при смене контейнера.
   - c) *Остановка:* гарантированная остановка контейнера по метке; только после неё — любой повтор (INV-14).
   - d) *Harvest:* на хосте, с отключёнными hooks, по правилам `harvest{}` пакета (§6.3): diff файлов рабочей копии
     против `base_commit` (локальная git-история контейнера отбрасывается; симлинки не разыменовываются, вне дерева —
     `forbidden_path`; ignore-список, лимиты размера, режим файлов нормализован) → reconcile: `undeclared_file`,
     `forbidden_path`, `core`, `judge_edit` (правка `protected[]`: `.sef/**`, политика, acceptance-тесты из снимка,
     конфигурация тестового раннера и гейтов, архитектурные тесты, конфиги движков, `.git*`, lock-файлы — если путь не
     входит в утверждённый `impact.write` задачи с `risk ≥ normal`), `artifact`, `dependency`, `secret`,
     `injection_suspect` (инструкции в добавленных комментариях/строках — не блокирует, подсвечивается в пакете ревью и
     метрике). Пересчёт пола риска по фактическому diff (§3.2). Чисто → коммит runner'ом с трейлерами `Sef-Work`,
     `Sef-Task`, `Sef-Attempt`, `Sef-Contract-Hash`, `Sef-Manifest`; публикация в `refs/sef/attempts/<id>`.
   - e) *Гейты:* очередь `gates`, контейнер гейтов на коммите попытки; перед запуском runner восстанавливает
     acceptance-тесты по blob-sha из снимка approval (`git cat-file`) в `.sef/acceptance/pending/<task>/` и запускает их явным
     путём, затем lane-гейты пакета;
     evidence привязан к `commit`, `manifest_sha` и blob-sha тестов; `infra_flaky` (гейт `ERROR`, сигнатура из списка
     пакета) → один перезапуск.
   - f) *Ревью по политике:* авторевью — профиль другого семейства по пакету ревью (diff с тестами, контракт из снимка,
     выводы гейтов, отметки `injection_suspect` и protected-файлы выделены; `residue[]`/`questions[]` — после
     валидации схемой и усечения; без транскрипта и отчёта исполнителя, INV-7; diff и остаток передаются как данные с
     рамкой недоверия); стол — ожидание `recv` до `sef review submit` с актором по классу (§3.3).
   - g) *`evaluate`* (чистая функция над evidence): `ACCEPTED` | `REPAIR` (новая попытка с находками в пределах бюджета;
     одинаковая сигнатура отказа — `(gate_id, нормализованный хвост вывода)` — дважды → эскалация) | `ESCALATE` (во
     входящие стола) | `REJECTED` (в т. ч. `abstain`, пустой diff при `done`). `ACCEPTED` — состояние попытки, **не
     изменение git**: дальше `ready_to_land` (в очереди `landing`) → `landed` — отдельные переходы с событиями.
3. **Workflow `landing`** (очередь = 1): rebase коммитов попытки на текущий `master` хаба; rebase задел файлы diff →
   повторное ревью по политике; интеграционные гейты; политика → авто или ожидание `sef land`; `push --ff-only`; `master`
   хаба ушёл за время гейтов → повтор с rebase (число повторов — конфиг, затем эскалация). Тот же коммит закрывает задачи
   (`resolution`) и добавляет остаток задачами `proposed`; правки `.sef/items/**` посадкой **генерируются заново на
   вершине после каждого rebase**, а не переносятся патчем (иначе конфликт с правками стола на каждой посадке);
   конфликт в items всё же случился → эскалация, не repair. Событие `landed` с полной родословной.
4. **После посадки:** детектор escapes (§9.2) → `escape.detected` → сброс trust ladder класса, заморозка автопосадки,
   `sef revert` готовит revert-коммит. **Stop-the-line (INV-19):** красный интеграционный гейт на `master` (сразу после
   посадки или по cron-гейту патруля) → пауза всей очереди `landing` + задача `proposed` «починить master» с высшим
   приоритетом; снятие — зелёный гейт или `sef resume --landing` владельцем. Запущенные попытки не останавливаются; **stale-правило:**
   попытка с `base_commit` старше красной отметки `master` сажается только после rebase и повторных гейтов (иначе квота
   горит на непосаживаемом).
5. **Патруль** (cron DBOS): «сироты» (контейнеры и worktree без живого workflow), зависшие workflows и workflows чужой
   `application_version`, возобновление после сброса квоты, возраст входящих, срок хранения evidence и
   `refs/sef/attempts/*`, cron-гейт `master` (интеграционные гейты пакета на вершине; красный → INV-19), `review_by`
   у `deferred`.

## 6. Контракты и состояние

### 6.1 Где что лежит

| Данные | Где | Кто пишет | Изменяемость |
|---|---|---|---|
| Задачи (`epic`, `task`, `question`, `finding`, `deferred`, `improvement`) | `.sef/items/<id>.md` в репозитории проекта | стол; посадка (закрытие, остаток) | коммитами |
| Снимок approval | `.sef/approvals/<work>-r<N>.json` | владелец (`sef work approve`) | неизменяем; изменение — новая ревизия |
| Пакет и политика проекта | `.sef/pack.yaml`, `.sef/policy.yaml`, `.sef/prompts/**`, `.sef/image/**` | Work в core-зоне, посадка вручную | коммитами |
| Конфиг экземпляра | вне репозиториев | владелец | событие `config.changed` |
| Журнал событий | `var/sef/journal/*.jsonl` | только `journal` | только дописывается |
| Артефакты попытки и evidence | `var/sef/attempts/<id>/` | runner | неизменяемы после терминального состояния |
| Состояние workflows, очередей, ожиданий | БД DBOS | DBOS | операционное |

**Один вопрос — один authority (P9):** намерение, контракт, approval, код, посадка — git (хаб); граф работ и статус
в git — задачи-файлы; durable-состояние исполнения — DBOS; факты и переходы — журнал; большие payload и evidence —
артефакты (content-addressed, `artifact_id = sha256(content)`). Журнал — не вторая БД: событие = тип, id, хеши,
время, переход состояния, `data` ограниченного размера (лимит — схема); транскрипты, выводы гейтов, diff — артефакты
по `refs[]`. Один и тот же authoritative-факт нигде не хранится дважды.

Статус выполнения задачи (в очереди, в работе, на ревью) живёт в DBOS; в git — только `proposed | open | deferred |
closed | cancelled`. **БД DBOS одноразовая:** её потеря → патруль останавливает сирот, все нетерминальные попытки →
`aborted` (событие), задачи возвращаются в ready; журнал содержит всё для аудита (события `attempt.*`), истина
намерений и результатов — в хабе (P6). `sef doctor` проверяет согласованность DBOS ↔ журнал ↔ хаб; восстановление
очередей из журнала — roadmap (§13).

### 6.2 Схемы (версия `sef/<name>/1`)

Правила схем: версия в каждом файле; неизвестные поля инструменты **сохраняют**; новая форма — новая версия, не мутация.

- **`sef/item/1`** — frontmatter задачи:
  `id` (`<prefix>-<6 символов base32>`, без коллизий при записи со стола и с посадки), `type`, `status`, `title`,
  `priority`, `labels[]`, `deps[{type: blocks|parent|discovered_from|related, id}]`, `source_ref`,
  `deferral{reason, trigger[], review_by}` (обязательно для `deferred`), `resolution{by, ref}` (для `closed`),
  `contract` (для `task`): `risk: trivial|small|normal|complex`, `impact{write[], create[], delete[]}` (globs),
  `acceptance[{text, verified_by}]`, `acceptance_tests[{path, blob_sha}]` (закоммичены до approve; blob-sha входит в
  `contract_hash`; защищены от правки исполнителем), `verification{gates[], commands[]}`, `budget{attempts, repair,
  review_cycles, wall_time_min, cost_usd}`, `stop_conditions[]`, `non_goals[]`, `escalation`. Тело — бриф для человека и
  агента. Готовность: неизвестный или неоднозначный id в `blocks` — «не готова»; на готовность влияет только `blocks`
  (`parent`, `discovered_from`, `related` — нет; явно, чтобы не повторить путаницу Beads). Коллизия id при посадке (тот
  же id, разное содержимое) → эскалация.
- **`sef/approval/1`:** `work`, `revision`, `items: {id: contract_hash}`, `base_commit` (коммит хаба, где живут
  утверждённые контракты и acceptance-тесты — не путать с `manifest.base_commit`), `pack_hash`, `policy_hash`, `budget`,
  `approved_by`, `approved_at`. Изменение контракта, пакета или политики после approve → `INVALID_APPROVAL`, нужна новая
  ревизия; новая ревизия **отменяет живые попытки** задачи (`aborted`, контейнер остановлен, бюджет новой ревизии не
  расходуется).
- **`sef/manifest/1`:** родословная (`work`, `task`, `parent_attempt`, `approval_revision`), движок (`adapter`,
  `profile_sha`, версия CLI и адаптера, запрошенная модель), оплата (`declared`, `attested`), аттестация репозиторных
  конфигов движка (`engine_config_check`), `image_digest`, `pack_hash`, `policy_hash`, `prompt_hashes`,
  `context_pack_sha`, песочница (бэкенд, монтирования, сетевая политика, пользователь, лимиты, `capabilities`),
  `credential_class` (`slot_auth|proxy_injected|none`), `application_version` (версия рантайма SEF), `base_commit`
  (вершина `master` при старте попытки), бюджет, резолюция политики (в т. ч. `risk` после `risk_floor`). Manifest —
  обязательная граница доверия: фиксируется до первого вызова модели и неизменяем (INV-4); вместе с evidence отвечает на
  «почему этот агент, модель, промпт, код и политика дали этот результат».
- **`sef/result/1`:** `status`, `summary` (недоверенное), `unverified_assumptions[]`, `residue[]` (черновики задач),
  `questions[]`, `changed_files[]`, `tests_claimed[]`, `errors[]` — **заявления** агента, harvest и гейты сверяют их с
  фактом (расхождение — сигнал в пакет ревью, не отказ). Читается из файла в рабочей копии (ACP структурированного вывода не даёт); невалидно → `INVALID_OUTPUT`.
- **`sef/event/1`:** `event_id` (ULID), `ts`, `type` (реестр типов; будущие типы — evals, A/B, `drift`, `security` —
  зарезервированы), `actor{kind: owner|desk|runner|engine, id}`, `project`, id родословной, версии (`manifest_sha`,
  `pack_hash`, `policy_hash`, `application_version`), типизированные `data`, `refs[{path, sha256}]`, `usage{tokens,
  cost_estimate_usd, shadow_cost_usd, billing}`, `durations`, `hash_prev` (sha256 предыдущей строки файла журнала —
  хеш-цепочка; `sef audit --verify` проверяет), `trace_id`/`span_id` (зарезервированы под экспорт OpenTelemetry; OTel
  журнал не заменяет — нет неизменяемости, одного писателя и хеш-цепочки, сэмплирование для аудита недопустимо). События
  `policy.resolved` и `evaluate.decided` несут `input → rule → decision → evidence` — решение воспроизводимо.

### 7.3 Аттестация оплаты (перед каждой попыткой, INV-5)

| Движок | Проверка |
|---|---|
| Codex (`codex-acp`) | `forced_login_method="chatgpt"` в конфиге; в env нет `CODEX_API_KEY`, `OPENAI_API_KEY`; `codex login status` → `Logged in using ChatGPT` |
| OpenCode | провайдер профиля совпадает с объявленной оплатой; ключи провайдера только у api-профилей; `cost` из `usage_update` доказательством подписки не считается |
| Claude CLI (если включат) | `--setting-sources user`; нет `ANTHROPIC_*`, `CLAUDE_CODE_USE_*`; `apiKeySource=none`; `isUsingOverage=false` |

Расхождение → отказ до вызова модели, слот выключается, эскалация (§8).

**Репозиторные конфиги движка (все движки).** OpenCode читает `opencode.json`/`.opencode/**` из cwd (провайдер, модель,
`permission`, MCP-серверы), Codex — проектные `.codex/**` и `AGENTS.md`, Claude — `.claude/settings.json`. Это тот же
канал подмены оплаты и прав, что закрыт для Claude флагом `--setting-sources user`, но не закрыт для исполнителей.
Поэтому аттестация включает проверку: файлы из `engine_config_paths` профиля в рабочей копии либо отсутствуют, либо
байт-в-байт совпадают с эталоном пакета (`.sef/engines/<profile>/`); иначе — отказ до вызова модели
(`ENGINE_CONFIG_MISMATCH`). Те же пути — в `protected[]` (правка исполнителем = `judge_edit`). Результат — в manifest
(`engine_config_check`).

### 7.4 Слоты авторизации

Refresh-токены Codex и OpenCode одноразовые, межпроцессной блокировки нет. **Слот движка** — постоянный volume с
собственным входом; слот переиспользуется последовательными попытками и никогда не делится двумя одновременно. N
параллельных линий движка = N слотов (паттерн Gas Town «постоянная идентичность, эфемерные сессии»). Работоспособность
нескольких входов одного аккаунта — спайк SP-4; запасной вариант — один сервер движка с сессиями на попытки.
**Стартовая ёмкость — 2 слота Codex** (несколько входов одного аккаунта — и технический, и договорной риск);
рост — по метрике времени в паузе квоты и отсутствию сигналов вендора, порог — конфиг. Второй исполнитель (OpenCode с
API-профилем) — источник ёмкости, не только семейство ревью.

### 7.5 Квота и ёмкость

- Параллельность — числом слотов; резерв ёмкости под ревью и посадку.
- Пауза до сброса: Codex — лимиты из статуса `codex-acp` и `usageLimitExceeded`; OpenCode — классификация текста ошибки и
  backoff. Каждая пауза — событие `quota.paused` с источником сигнала.
- Бюджеты api-профилей — SEF по событиям `usage`; дополнительно — лимиты трат в консолях вендоров.

### 7.6 Безопасность и версии

- Версия бэкенда песочницы (Docker Engine; при SP-12 — VMM Docker Sandboxes) закрепляется как часть границы
  безопасности: обновление — Work с прогоном docker-тестов §11, не автообновление.

- Egress только к доменам вендора; секреты вычищаются из diff, вывода и журнала; `sef engines rotate <slot>` — ротация.
- Версии `codex-acp`, OpenCode и CLI закреплены в образе пакета; записанные ACP-потоки — контрактные тесты адаптера;
  обновление движка — Work с прогоном контрактных тестов.
- Фактическая модель проверяется на каждом ходу; расхождение с профилем → `INVALID_OUTPUT`; смена модели сбрасывает trust
  ladder.

## 8. Отказы и восстановление

### 8.1 Класс → действие (данные политики)

| Класс | Действие |
|---|---|
| `QUOTA_EXHAUSTED` | пауза очереди слота до сброса (неизвестно — backoff); задача ждёт, бюджет не тратится |
| `RATE_LIMIT_TRANSIENT`, `SERVER_OVERLOAD`, падение адаптера/сессии | рестарт сессии в той же попытке ≤ N (профиль, событие `session.restarted`) → затем как `EXECUTION_FAILURE` |
| `TIMEOUT`, `EXECUTION_FAILURE` | остановить контейнер → технический повтор новой попыткой ≤ N (профиль) → эскалация |
| `AUTH_FAILURE`, расхождение аттестации | выключить слот, эскалация |
| `INVALID_OUTPUT` (невалидный `sef/result/1`, смена модели, пустой diff при `done`) | один повтор с напоминанием схемы → эскалация |
| `ENGINE_CONFIG_MISMATCH` (репозиторный конфиг движка отличается от эталона пакета) | отказ до вызова модели; эскалация: отравлен репозиторий или устарел эталон |
| `abstain` | `REJECTED` с причиной во входящих: стол переформулирует или отменяет; повторной попытки нет |
| `blocked`, `needs_decision` | задача `question` во входящие; попытка завершается (контейнер остановлен, слот свободен); workflow ждёт ответа (`recv`); ответ — в context pack новой попытки |
| `scope_exceeded`, `undeclared_file` | один repair: вернуть перечисленные файлы, scope не расширяется; иначе эскалация |
| `forbidden_path`, `core`, `secret`, `judge_edit` | отказ без repair, эскалация (`judge_edit` protected-пути внутри утверждённого `impact.write` задачи `risk ≥ normal` — не нарушение, но файлы выделены в пакете ревью, вердикт — `owner`) |
| `injection_suspect` | не блокирует; подсветка в пакете ревью; метрика; при `secret`/`judge_edit` в той же попытке — эскалация |
| `risk.escalated` (пол риска по фактическому diff выше объявленного) | политика перерезолвится; класс, требующий стола, → входящие; попытка не отбрасывается |
| гейт `FAILED` | repair с выводом гейта в пределах бюджета; та же сигнатура дважды → эскалация |
| гейт `ERROR`, `infra_flaky` | один перезапуск гейта → блок `infra` + алерт |
| ревью `CHANGES_REQUESTED` | repair с находками ≤ `review_cycles` |
| конфликт rebase | repair на конфликтных файлах или эскалация; конфликт в `.sef/items/**` — только эскалация |
| интеграционный гейт красный до посадки | не сажать; repair или эскалация |
| красный `master` (после посадки или cron-гейт) | INV-19: пауза очереди `landing`, задача «починить master», заморозка класса-виновника, сброс trust ladder |
| escape после посадки | `sef revert` (вручную или авто по политике), заморозка класса, сброс trust ladder |
| краш диспетчера | DBOS продолжает с шага (`start` идемпотентен по метке, §5 2b); патруль сначала останавливает «сирот»; прерванная попытка — `aborted`, новая попытка |
| обновление диспетчера / чужая `application_version` | только через `sef stop --all` → drain → замена → `resume` (§4.2); workflows чужой версии патруль помечает и эскалирует |
| потеря БД DBOS | сироты остановлены, нетерминальные попытки `aborted`, задачи → ready (§6.1) |
| отмена владельцем (`sef stop`, новая ревизия approval) | попытка `aborted` на границе `poll`; бюджет учитывается в метриках, не в лимите новой ревизии |
| исчерпан бюджет Work | `BUDGET_EXHAUSTED` → входящие стола |

### 8.2 Громкость

Каждый отказ, требующий человека, попадает во входящие (`sef inbox`) и в `sef status`; ничего не остаётся только в
журнале (INV-15). Уведомления вне CLI (Telegram, push) — roadmap, шов `notifier` поверх событий.

## 9. Метрики и аудит

### 9.1 Источники и вычисление

Факты — журнал событий и git (посадки, revert, трейлеры). Метрики — версионируемые SQL-представления
`sef/metrics/*.sql`, исполняемые DuckDB поверх JSONL журнала. Определение метрики фиксируется до сравнения; изменение —
новая версия представления. **Теневая цена:** расход на подписке считается в единой единице — токены × прайс-лист
модели (таблица в конфиге экземпляра, версионируется) → `shadow_cost_usd`; так профили на подписке и API сравнимы;
фактическая оплата (`billing`) хранится отдельно.

### 9.2 Набор метрик MVP

| Группа | Метрики |
|---|---|
| Поток | lead time (approve → landed); время этапов (очередь, агент, гейты, ожидание стола, посадка); WIP; глубина очередей; throughput принятого |
| Качество | pass@1 (принято с первой попытки) с распределением по повторам; repair на задачу; классы отказов гейтов; находки ревью по слою и серьёзности; нарушения scope по классам; **escapes и долговечность** на контрольных точках 7 и 30 дней; **review-miss по слоям** (гейты, авторевью, стол); доля flaky |
| Стоимость и ёмкость | токены по категориям (успех, провал, повторы, ревью); оценка стоимости; время в паузе квоты; CPU-минуты гейтов; **стоимость принятого долговечного результата** (все атрибутируемые затраты, включая провалы, переделки и время стола, на принятые и ещё действующие результаты) |
| Внимание человека | элементов стола на задачу; время от входящих до решения |
| Автономность и доверие | доля авторевью и автопосадок по классам; касания человека на задачу; состояние trust ladder; отзывы автономии |
| Сравнение | срезы по движку, модели, профилю, промпту, пакету и политике из manifest — только при одинаковых классе, окне и числе прогонов |

**Escape** — revert коммита с трейлером `Sef-Attempt`; красный `master` на интеграции после посадки; finding со ссылкой на
попытку; находка выборочного чтения стола.

### 9.3 Правила против Goodhart

- Метрики активности (токены, PR, строки кода) — не цели.
- Самоотчёт агента — никогда не метрика и не evidence приёмки.
- Качество всегда связано с поздними исходами (долговечность, escapes).
- Грейдер (гейт, ревьюер) реально запускается и воспроизводим; его пропуски и ложные тревоги измеряются.

### 9.4 Аудит

`sef audit <task|attempt|landing>` — родословная от намерения до поздних исходов: задача и снимок approval; попытки
(manifest, события, гейты, ревью, решения с автором); посадка — кандидат, исходное и целевое состояние, полномочие (правило
политики или автор), evidence-обоснование, путь восстановления (`sef revert`); revert, escapes, findings. Журнал только
дописывается одним писателем, секреты вычищены, срок хранения evidence задан конфигом; `sef audit --verify` проверяет
хеш-цепочку `hash_prev` (подмена или обрыв строк журнала обнаруживаются).

### 9.5 Контур улучшения

1. `sef report weekly` → стол, скилл `sef-analyze`.
2. Задача `improvement` с манифестом: какой провал лечит, предсказанный эффект, риск, метрики наблюдения, правило отката.
3. Обычный Work; промпт, пакет и политика — core-зона, посадка вручную; меняемый компонент не переписывает своих судей
   (INV-9).
4. Оценка «до/после» по версиям из журнала; не сбылось — откат.

Roadmap (§13): selection evals на сохранённых попытках, A/B с заранее заданным правилом остановки, абляция при выходе
модели. Основа сейчас: попытка воспроизводима (`base_commit`, контракт, хеши пакета и промптов, digest образа), типы
событий зарезервированы.

## 10. Инварианты SEF

Каждый инвариант имеет исполняемый контроль; тест пишется до кода среза, в котором инвариант активируется. Соответствие
прежним SEF-1…67 — приложение C.

| ID | Инвариант | Контроль | Срез |
|---|---|---|---|
| INV-1 | Агент никогда не пишет в репозитории фабрики: в его контейнере нет доступа к хабу и рабочему репозиторию фабрики и нет учёток (одноразовый локальный git без remotes допустим, его история отбрасывается). Коммит делает только runner; `master` меняет только `gitops.land` (`push --ff-only`); `refs/sef/attempts/*` пишет только runner | тест монтирований и remotes локального git; AST: merge/push только в `sef.gitops` | S1 |

## 15. Процесс разработки

- **План = срезы.** Индекс срезов + подробный план только текущего среза. Бриф задачи: Goal, Changes, Files, Tests, DoD —
  **без полного кода** (противоречия внутри брифов с кодом дали большую часть решений fac0).
- **Исполнение:** субагент на задачу; один совмещённый ревьюер (соответствие брифу + качество) и не больше одного раунда
  правок; Critical/Important чинятся, Minor → задача остатка.
- **Отчёт** — одна страница: что изменено, последние строки прогонов, отклонения, id остатка, стоимость.
- **Rulings** — только при изменении интерфейса, контракта или инварианта; остальное — строкой отчёта.
- **Самоприменение:** с S1 задачи `sef` проходят стол ревью SEF; с S3 — авторевью.
- Правило «одна крупная задача — одна сессия» сохраняется.

Состояние Change (`change_state`) — authority WARRANT (record); статус исполнения item — SEF. `tasks.md` чекбокс TASK — WARRANT/OpenSpec; item `closed` — SEF; расхождение ловит `warrant analyze` (`CONFLICT`) при посадке | ADR-0009, ADR-0010, ADR-0020 п. 3, 11 | S1 |

### F.2 Задача, approval, попытка

| # | Раздел SEF | Что учесть | Решение / обоснование | Срез |
|---|---|---|---|---|
| W-06 | §5 0, §6.2 `sef/approval/1` | `sef work approve` в коммите снимка вызывает `warrant transition <change> APPROVED --ref sef://<project>/approval/<work>-r<N>@<commit>`. CLI сам пересчитывает gates `SPECIFIED→APPROVED` (кроме `human-approval`, которым и является этот approve); отказ CLI (exit ≠ 0) → approve отклонён. Полей снимка не добавляем | ADR-0020 п. 8, 11; ADR-0011 п. 3 (транзиции едут в коммите следующего шага) | S1 |
| W-07 | §5 2a context pack | Context pack попытки включает Context Pack WARRANT: `warrant run start <change> --task <TASK> --json` отдаёт `rules[]` (правила по путям, пересекающие `write_scope`), `write_scope[]`, `context_hash`. `context_pack_sha` покрывает оба; `write_scope` WARRANT ⊆ `impact.write` item (иначе `sef work validate` отказ). Run создаёт SEF при prepare (закрывает вопрос «кто создаёт Run», 11 §4 WARRANT) | ADR-0022 п. 6; 07 §4 WARRANT; ADR-0018 п. 6 | S1 |

| W-09 | §4.4 рабочая копия, §5 2d harvest, §6.3 `protected[]` | В `sef-hub` `.warrant/runs/**` и `.warrant/evidence/**` **не пишутся в рабочую копию**: CLI WARRANT читает `WARRANT_STATE_DIR` (долг kernel) → `var/sef/attempts/<id>/warrant/`; Run, `guard_events[]`, hints и evidence попытки — артефакты попытки (`refs[]` журнала, content-addressed). `.warrant/**` остаётся в `protected[]` целиком; harvest не видит правок WARRANT-состояния | ADR-0020 п. 13; ADR-0021 п. 1; 03 §4 WARRANT («внешнее хранение Run — later» — триггер: S1 SEF). Иначе каждая попытка даёт `judge_edit` → класс `normal`, вердикт `owner` (ревью I-F-8) | S1 |
| W-10 | §6.3 `protected[]` проекта под WARRANT | `protected[]` ⊇ `.warrant/**`, `openspec/schemas/**`, `openspec/config.yaml`, `openspec/specs/**`, `openspec/changes/archive/**`, `AGENTS.md`, `.codex/**` (последние два уже в дефолте). Дублируется вручную; `warrant validate` → `SEF_PROTECTED_DRIFT`. `warrant sync` в `.sef/**` не пишет. Исключение через `impact.write` каждого item: `openspec/changes/<change>/tasks.md` (чекбоксы TASK) и пути кода | ADR-0020 п. 13; ADR-0021 п. 1–2; ADR-0022 п. 5 | S1 |
| W-11 | §6.3 `engines{<profile>}`, §7.3 аттестация конфигов | Эталон `.sef/engines/<profile>/` для `.codex/hooks.json` и `AGENTS.md` = вывод `warrant sync` на текущем `pack_hash`: шаг сборки пакета проекта запускает `warrant sync` и копирует файлы в эталон. Иначе после любой правки правил WARRANT каждая попытка падает с `ENGINE_CONFIG_MISMATCH`. Определение hook — постоянная строка `warrant guard --frontend codex`; trust hook Codex выдаётся в образе или слоте (§7.4) | ADR-0018 п. 4; ADR-0020 п. 14; ADR-0022 п. 5 | S0b (эталон), S1 |
| W-12 | §5 2e гейты, §6.3 `gates{lane[], integration[]}` | Тесты — один гейт: `warrant verify --transition VERIFYING->MERGED --base <commit>` как lane- и integration-гейт; отдельного `pytest`-гейта нет. Acceptance-тесты `.sef/acceptance/{pending,active}/**` входят в `paths.tests` `warrant.json` проекта и запускаются check `tests-passed` внутри `verify` — явный запуск в 2e не нужен (двойной прогон). Cron-гейт `master` (`pytest .sef/acceptance/active`) — механизм INV-19, не evidence Change, остаётся. В `sef-hub` `verify` для `→MERGED` **не** считает `human-approval` (как CI spec-PR в `github`); одобрение владельца = ручная `sef land` (актор `owner`), её ref идёт в `transition MERGED` (W-14) | ADR-0020 п. 10; ADR-0011 Consequences | S1 |
| W-13 | §2.4, §5 2e, INV-9 «судья из base» | Policy-пути WARRANT — тоже судья: в контейнере гейтов `.warrant/**`, `packs/**`, `openspec/schemas/**`, `openspec/config.yaml` восстанавливаются из `manifest.base_commit`, если `impact.write` item их не включает (не `factory-change`). | W-14 | §5 3 landing, §6.1 | Посадка **не последнего** item Change: record WARRANT не трогается (между посадками `warrant status` показывает `STALE` — штатно). Посадка **последнего** item: коммит посадки несёт `APPROVED→IMPLEMENTING→VERIFYING→MERGED` с refs `sef://<project>/attempt/<id>`, `…/attempt/<id>/gate/<gate-id>`, `…/landing/<id>` (актор посадки), следующим коммитом — `warrant archive <change>` (gates `MERGED→ARCHIVED` — integration-гейты; конфликт `openspec archive` → `sef inbox`). Landing — доверенный писатель `openspec/specs/**` и `openspec/changes/archive/**` (как для `.sef/items/**`); `protected[]` ограничивает попытки, не landing. Item закрывается, только если TASK отмечен в `tasks.md` (иначе `warrant analyze` → `CONFLICT` → эскалация, не repair) | ADR-0020 п. 11–12 (уточнение: `MERGED` один раз на Change); ADR-0021; 04 §2 WARRANT; ревью I-F-7 | S1 |
| W-15 | §6.2 approval, §5 2e | Gate `spec-approved` (core-sdd, транспортно-нейтральный): hash дерева `{proposal.md, design.md, specs/**}` каталога `openspec/changes/<change>/` на коммите из ref перехода `APPROVED` ↔ то же дерево на `manifest.base_commit`; `tasks.md` исключён (правится при реализации). Расхождение → `STALE`, нужна новая ревизия approval (`INVALID_APPROVAL` SEF — тот же смысл). Новых полей снимка не нужно | ADR-0020 п. 9 (уточнение); ревью I-F-6, I-F-18 | S1 |
| W-16 | §5 2g `evaluate` | Verdict gates WARRANT — evidence для `evaluate`: `FAIL` non-waivable → `REPAIR`/`ESCALATE` по политике SEF; `WAIT` (`gate-failed-waivable`, `pending_approvals`, `blocking_unknowns`) → гейт не зелёный, ждать стола; `warrant next` в попытках не используется — controller WARRANT работает для стола | ADR-0020 п. 1; 04 §4 WARRANT | S1 |
| W-17 | §6.2 `sef/result/1`, §8.1 `needs_decision` | `needs_decision` → `question` во входящие.
