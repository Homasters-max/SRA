# 01 — git как системный процесс

## Проблема

Процесс git держится на прозе и памяти, а не на процедурах и проверках (правило «о форме — проверкой», R-14…R-16).

| Правило | Где сейчас | Что уже случалось |
|---|---|---|
| Одна ветка — один worktree, ветку проверять перед коммитом | `CLAUDE.md`, `rules.md`: держится шагом 1 навыка `group-done` — только в группах задач | коммит `d2d8fd3` ушёл не в ту ветку, когда сессии переключали ветку в общем `D:\project\SRA` (фаза 2) |
| Текст коммита и PR — файлом (`-F`, `--body-file`) | `CLAUDE.md` «Язык и документы», память — проза без проверки | PowerShell подставил `${0%/*}` и `$(dirname)` в `-m` — текст коммита потерян (фаза 3) |
| impl-PR — только merge commit | I-97, `transition MERGED` → `COMMIT_NOT_MERGED` (R-1) | держится только при `transition`; GitHub разрешает squash и rebase |
| `gh pr merge` без `--delete-branch` | память | `--delete-branch` удаляет worktree этой ветки |
| Merge делает человек | память «blocked step → give command» | классификатор auto mode дважды блокировал `gh pr merge` (phase-3b) |
| Список worktree и потоков | **решено ADR-0032**: `brief.js` (worktree, файлы передачи в каждом) | — |
| Слитые ветки удаляются | нигде; `brief.js` показывает только локальные | на 2026-09-24 не удалены 8 локальных и 21 на origin |
| Один поток — одна цель | нигде | 2026-09-24 две параллельные сессии открыли потоки с одной целью: `git-flow` (сессия реализации ADR-0032, по п. 12) и `skills-git-hygiene` (черновики); дубль нашли после merge, `git-flow` влит в этот поток |

Префиксы веток на практике: `spec/`, `worktree/`, `archive/` (ADR-0011; CI выводит Change из `worktree/<change>`),
`process/`, `docs/`, `fix/`; `feature/` — наследие фаз 1–2. Заголовки коммитов на практике: `<change>: …`,
`process: …`, `docs: …` — не проверяются. Параллельные сессии — норма (2026-09-24 — до трёх worktree одновременно). `git rebase -i` в среде агента не работает; shell — Git Bash или PowerShell.

Готовые приёмы агента `git-workflow-master` из каталога противоречат нашим нормам:
- rebase перед merge и squash — нарушают I-97;
- локальный `git merge --no-ff` в `main` — ADR-0011 п. 3 запрещает коммиты в `main` вне PR;
- удаление ветки сразу после merge — удаляет её worktree;
- conventional commits — у нас префикс Change.

Взять из него можно только «показывай безопасную версию опасной команды и путь восстановления».

## Идея

Процедуры git — навыки по стандарту ADR-0032 п. 6. Нормы остаются в ADR-0011, I-97 и новом ADR по итогам этого
grilling. Форма держится хуками и CI там, где это возможно.

| Процедура | Шаги |
|---|---|
| **старт** | нет ли потока с той же целью (файлы передачи из `brief.js`) → `git fetch` → `git worktree add ../SRA-<имя> -b <префикс>/<имя> origin/main` → `npm ci && npm run build` в worktree → файл передачи потока |
| **где я** | `brief.js` уже даёт ветку, worktree и изменения; навык добавляет совпадение worktree и ветки, ahead/behind, PR ветки. Сейчас сверка ветки копируется в `group-done` и `decision` |
| **коммит** | сверить ветку с worktree → текст в scratchpad → `git commit -F` → заголовок `<префикс>: …` → строка соавторства |
| **PR** | `git push -u` → `gh pr create --body-file`; шаблон по виду PR: что по ADR-0011 должен нести spec-, impl- или archive-PR |
| **передача merge** | напечатать `gh pr merge <N> --merge` и строку «что делать». Merge — акт maintainer'а |
| **после merge** | из `D:\project\SRA`: `git pull --ff-only` → `git worktree remove` → `git branch -d` → `git push origin --delete` |
| **чистка** | слитые ветки без worktree, worktree слитых веток, ветки на origin — список и удаление после подтверждения (пересекается с 03) |
| **восстановление** | справочник: коммит не в ту ветку (`cherry-pick` в свою ветку, `git reset --keep` в неопубликованной чужой); конфликты `docs/handoff/*`, `docs/backlog.md`, номеров I-N; `reflog`. Главное правило — **не переписывать историю после того, как SHA попал в evidence, `--commit` или PR** |

## Вопросы для grilling

❓ **G1 — Один навык или несколько.** Восемь процедур не помещаются в 80 строк. Варианты:
- (a) `git-start` (старт, где я, коммит) + `git-land` (PR, передача merge, после merge, чистка) + справочник
  `git-land/recovery.md`;
- (b) по навыку на процедуру;
- (c) один `git-flow` и справочники.

➡️ (a): два навыка по фазам работы, восстановление — справочником.

❓ **G2 — Канонические префиксы веток.** Набор: `spec/`, `worktree/`, `archive/` (Change), `process/` (ADR и
реализация процесса), `docs/` (только документы), `fix/` (исправление вне Change). `feature/` — снять. Проверка — шаг
CI (неизвестный префикс → ошибка) или хук на `git worktree add -b` / `git checkout -b`.

➡️ Набор принять. Проверка — шаг CI: работает и для людей, и для любого агента.

❓ **G3 — `D:\project\SRA` всегда на `main`.** Вся работа — в worktree. Хук `PreToolUse` запрещает агенту в основном
checkout `git checkout` / `git switch` на другую ветку и любой `git commit` (в `main` вне PR коммитить нельзя по
ADR-0011 п. 3). Так правило «одна ветка — один worktree» перестаёт быть прозой.

➡️ Принять. Хук — для основной сессии и субагентов (сквозной вопрос X3).

❓ **G4 — Политика merge на стороне сервера.** Branch protection недоступна (приватный репозиторий, бесплатный план).
Доступно в настройках репозитория: выключить squash и rebase (`allow_squash_merge`, `allow_rebase_merge` = false) —
тогда I-97 держит сам GitHub; `delete_branch_on_merge` оставить `false`. Проверка — шаг CI или `brief.js` читает
настройки через `gh api` (сеть — только в ручном вызове). Отдельно: обязательное review из ADR-0011 не держится ничем.
Варианты: принять и записать поправкой к ADR-0011 / перейти на публичный репозиторий или GitHub Pro.

➡️ Выключить squash и rebase (меняет maintainer в настройках). Разрыв с ADR-0011 записать поправкой: review держит
процесс, а не GitHub, до смены плана.

❓ **G5 — Заголовок коммита.** Правило: `<change>: …` в ветках Change, `<префикс ветки>: …` в остальных. Проверка — шаг
CI по коммитам PR, или хук `commit-msg`, или не проверять.

➡️ Шаг CI по коммитам PR — дёшево и видно в PR.

❓ **G5a — Текст через файл: шаг навыка или правило.** Сейчас это проза `CLAUDE.md` и память. Проверить нельзя: искажённый
PowerShell текст выглядит как обычный. Вариант — шаг «коммит» навыка `git-start` (всегда `-F` из scratchpad) плюс
строка в `CLAUDE.md` для работы вне навыка.

➡️ Шаг навыка; строку в `CLAUDE.md` оставить. Правило о форме без проверки — пометить в `rules.md` как держащееся
навыком.

❓ **G6 — Force push.** Агенту запретить `git push --force` и `--force-with-lease` хуком. Переписать историю
неопубликованной ветки можно без force.

➡️ Запретить. Исключение — только командой maintainer'а вручную.

❓ **G7 — Кто и когда чистит.** Варианты:
- (a) процедура «после merge» — сразу после каждого merge;
- (b) плюс «чистка» раз в поток;
- (c) `brief.js` только показывает — уже есть для локальных веток; ветки на origin он не видит (без сети,
  `git branch -r` после `fetch --prune` — сеть не нужна, но данные устаревают до `fetch`).

➡️ (a) + (c). «Чистка» — часть навыка гигиены (03), удаление — после подтверждения. В `brief.js` добавить счётчик
слитых `origin/*` по последнему `fetch`.

❓ **G8 — Инструменты среды или только git/gh.** Desktop-приложение даёт `sync_with_base_branch`, монитор PR и
Auto-fix, но навык должен работать и в CLI, и в Codex (фаза 4).

➡️ Только git/gh. Инструменты приложения — необязательная подсказка в «Шагах».

❓ **G9 — Дубли потоков.** Перед тем как открыть поток, проверить, нет ли потока с той же целью: файлы передачи всех
worktree и `main` (`brief.js`), `docs/drafts/*`, строки `backlog.md` с «Куда: поток …». Варианты:
- (a) шаг «старт» и навыка `handoff`;
- (b) реестр потоков (файл);
- (c) имя потока = имя ветки, чтобы дубль был виден сразу.

➡️ (a): реестр был бы вторым местом того же знания (ADR-0032 п. 1).

## Вне объёма

- `warrant ci` (фаза 4): вывод Change из ветки и проверка топологии PR — продуктовая норма, не дублировать.
- Права `GIT_PUSH` / `OPEN_PR` агента (ADR-0011 Consequences) — фаза 4 и SEF.
- Перенос навыков в pack `core-sdd` как рецепта для целевых проектов — после фазы 4.
