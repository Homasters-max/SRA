# Тёмная фабрика: человек до запуска — принятые решения Q1–Q7 (grilling 2026-09-29)

Решения maintainer'а, принятые в grilling 2026-09-29 после PR #101–#107. Это вход ADR-0050: решения не гриллить заново, а записать нормой. Схема фабрики, которую они перестраивают, — [02-scheme-v2](02-scheme-v2.md).

## Проблема

ADR-0049 (принят 2026-09-29) держит человека **между стадиями** Change:
- merge spec-PR и impl-PR человеком (п. 2);
- одобрение spec без человека только для LOW и только с волны 3 (п. 5);
- «очередь решений» в `flow status` (п. 1, `process/flow.md` §4).

Сессия того же дня показала цену этого: агент просил «Enable auto-merge», спрашивал про флейк, откладывал ответы. Maintainer сформулировал целевую модель иначе — ниже.

Факты на 2026-09-29 (HEAD `1941ef3`, CLI 0.8.3):
- судья (`packages/cli/src/core/ci/refs.ts:129-146`) принимает ref `APPROVED` / `MERGED`, только если PR слил член роли одобрения (`roles.maintainer` = `Homasters-max`), а при заданных `identities.agents` — не агент и не автор PR. При пустых approvals `approvalRoles` (`core/roles.ts:42`) откатывается к fallback-роли. Значит, merge impl-PR ботом судья сейчас не засчитывает никогда;
- агент работает как машинный пользователь `homasters` («WARRANT agent», id 52467145): `GH_TOKEN` в `env` файла `C:\Users\Xiaomi\.claude\settings.json`, scopes `repo`, `workflow`, collaborator `Homasters-max/SRA` с `write`. `gh` в обычном терминале maintainer'а — `Homasters-max`;
- оверлей `risk-high` добавляет `human-approval` на `VERIFYING->MERGED`, а почти любой Change самого SRA — `factory-change` HIGH (`packages/cli/src/**`, `packs/**`, workflow).

## Идея

**Цель:** human starts a Change; machine owns the lifecycle until terminal outcome.

```text
INPUT:   одобренная spec + tasks   (единственный акт человека — запуск)
           ↓
         автономное исполнение
           ↓
         retry / diagnose / repair / re-run
           ↓
         verify → merge → release
           ↓
OUTPUT:  PASS | FAIL + полный отчёт   (FAIL — тоже конечный результат)
```

Человек стоит **до запуска** (спрос, spec, policy) и **после результата** (чтение отчёта, выборочный аудит, решение о повторе или отказе). Внутри цикла человека нет, кроме сознательного исключения Q2 и временного узла до 0.9.0 (Q7).

### Q1. Запуск — merge spec-PR maintainer'ом

- Одобрение spec и есть запуск. Вход фабрики — одобренная spec и tasks.
- Акт уже проверяем судьёй: `merged_by` из роли maintainer, ref `APPROVED`.
- Для работы без spec (docs, fix без policy-путей) запуск — метка `ready` на задаче: issue или строка backlog.
- Метка `ready` на намерении, которое требует spec, — сигнал «напиши spec». Spec пишет агент, maintainer одобряет её merge'ем spec-PR.
- Отвергнуто:
  - B — `ready` сразу запускает всё, spec утверждает review-субагент. Review пока независим условно: та же семья моделей, без attestation (WS-20, BL-28). Вернуться для LOW, когда у review будет attestation;
  - C — одобрение review «Approve», merge ботом: тот же результат, но нужна новая проверка в судье.

### Q2. Исключение после запуска — только самомодификация контура доверия

- После запуска человек нужен **только** при приёмке impl, который меняет контур доверия фабрики:
  - код судьи: `packages/cli/src/core/ci/**`, `packages/cli/src/core/gates/**`;
  - policy: `packs/**`, `.warrant/**` кроме состояния Change (`changes/`, `evidence/`, `runs/`);
  - защита агента: `.claude/**`, `**/AGENTS.md`, `CLAUDE.md`, `scripts/dev/*-hook.js`;
  - workflow: `.github/workflows/**`.
- Остальной HIGH (продуктовый код, тесты, документы) после одобренной spec машина доводит сама: gates, судья, ревью реализации (Q6).
- Реализация — цикл 1:
  - класс путей «контур доверия» в policy с `human-approval` на `MERGED` — вместо `human-approval` у всего `risk-high`;
  - судья засчитывает merge бота на `MERGED`, где effective policy не требует `human-approval`.
- Почему: фабрика, которая сама меняет судью и свою защиту без второго взгляда, — ANT-032 в худшем виде.
- Отвергнуто: A — исключение весь HIGH (SRA никогда не станет тёмным); C — исключений нет.

### Q3. FAIL — конец прогона, отчёт — в spec-PR

- **FAIL завершает прогон, а не Change.** Change остаётся в своём состоянии (обычно `IMPLEMENTING` / `VERIFYING`), PR переводится в draft, ветка и worktree сохраняются. Повтор — после правки человека (чаще всего новой spec, одобренной тем же актом Q1).
- `ABANDONED` — решение человека: оно необратимо.
- **Отчёт PASS или FAIL** — комментарием бота в spec-PR, где был запуск. Запуск и результат в одной ветке обсуждения, уведомление GitHub.
- Отчёт самодостаточен: ссылки на логи — справочно, решать по ним ничего не нужно. Состав:
  - итог PASS / FAIL и стадия;
  - что машина пробовала: повторы, исправления, их число и бюджет;
  - последний вердикт судьи со ссылками на evidence;
  - класс причины FAIL: `spec` (нужна правка утверждённой spec), `budget`, `judge` (судья отказал), `human` (исключение Q2), `infra`;
  - находки ревью реализации с пометкой advisory (Q6);
  - для PASS — PR, merge-коммиты, тег, итог канарейки.
- Отвергнуто: B — FAIL ведёт в `ABANDONED` (выбрасывает работу); C — закрыть PR и удалить ветку. Отчёт в отдельном issue или только в `flow status` — хуже: второе место чтения.

### Q4. Бюджет машины — константы `flow.js` v0

| Класс сбоя | Как узнаётся | Что делает машина | Предел |
|---|---|---|---|
| Инфраструктура, известный флейк | код 4 / `retryable` (WS-06, в 0.9.0); до того — список известных флейков в `flow.js` | перезапуск всего run (`gh run rerun <run>`, не `--failed`, BL-72) | 2 перезапуска → FAIL `infra` |
| Нарушение правила: gate FAIL, красный тест | вердикт судьи | диагноз → исправление → коммит → снова | 2 попытки на один и тот же сбой → FAIL `judge` |
| Любые исправления за прогон | счётчик flow | — | 5 → FAIL `budget` |
| Ревью реализации: BLOCKER | ревьюер (Q6) | исправление → новый раунд | 2 раунда → FAIL `budget` |
| Время прогона | от запуска до результата | — | 6 ч → FAIL `budget` |

- **Поправка maintainer'а к Q4:** FAIL `spec` — **только когда требуется изменить утверждённое намерение или spec**: delta specs, REQ/SCN, non-goals, границы proposal. Исправления реализации в рамках текущей spec машина делает сама, включая решения по ходу реализации строками `I-N` в design.md, если они spec не меняют.
- Нужна приёмка по исключению Q2 — машина доводит до готового к merge impl-PR, затем отчёт класса `human` («нужна приёмка контура доверия»). Это не провал работы, а конец прогона.
- Числа — константы `flow.js` v0. Настройка в `warrant.json` — при поставке flow (волна 4). Пересмотр порогов — после 10 прогонов, по метрикам повторов flow (строка backlog).
- Отвергнуто: B — сразу секция в `config/1` (правка CLI, а цикл 1 занят судьёй); C — бюджет в spec каждого Change (бюджет — policy фабрики, а не свойство Change).

### Q5. Исполнитель: сначала локально по расписанию, цель — по событию в облаке

- **Сейчас (A):** задача по расписанию в приложении Claude Code на машине maintainer'а, например раз в 30 минут.
  - Она смотрит `flow status`: есть ли Change, у которых spec-PR слит (`SPECIFIED`), а прогон не закончен.
  - Если есть — ведёт их до PASS или FAIL.
  - Подписка maintainer'а, проверенные хуки, навыки, worktree и `GH_TOKEN` бота. Минус: машина и Claude Code должны работать.
- **Цель (B):** GitHub Actions workflow на push в `main` (merge spec-PR) запускает headless Claude Code с секретами `ANTHROPIC_API_KEY` и PAT бота. Переход — при поставке flow (волна 4), вместе с решениями:
  - секреты в репозитории;
  - исполнитель отделён от судьи: отдельный workflow, запись только ботом, судья по-прежнему судит PR и в репозиторий не пишет (ADR-0010 п. 1).
- Облачная routine Claude Code (C) — запасной вариант: Windows-специфику (`git-hook.js`, пути) пришлось бы проверять заново.

### Q6. Ревью реализации — обязательный шаг flow, advisory

- Flow всегда запускает независимого ревьюера (агент `reviewer`, навык `review-impl`) на diff до `IMPLEMENTING->VERIFYING`:
  - BLOCKER — исправление и новый раунд, ≤ 2 по Q4;
  - MAJOR — исправление или строка backlog с обоснованием;
  - находки — в отчёт Q3.
- **Поправка maintainer'а к Q6:** до attestation ревью — **advisory evidence** и никогда не создаёт видимость доказательства:
  - не gate, судья его не засчитывает;
  - в отчёте помечено «advisory, не доказательство»;
  - если сохраняется в репозитории, то в форме, которую gates не читают как `review` `PROVEN`.
- Gate с evidence — когда у ревью будут attestation (WS-20) и другая семья моделей (BL-28): цикл 2 и позже.
- Отвергнуто: A — сразу gate (самоотчёт исполнителя под видом независимой проверки, ANT-032, схема v2 §13.6); C — без ревью (без человека на приёмке это единственный взгляд на смысл кода).

### Q7. Оформление и временный узел до 0.9.0

- **ADR-0050 «Тёмная фабрика: человек до запуска»** — Q1–Q6 нормой. Меняет ADR-0049 п. 1, 2, 5, 8 и ADR-0047 п. 1–2. Пометка «уточнён 0050» — в индексе ADR у 0047 и 0049.
- **`docs/process/dark-factory.md`** — схема v2 ([02-scheme-v2](02-scheme-v2.md)), перестроенная под модель: узлы человека только до запуска и после результата, у каждого временного — условие удаления. Что перестроить — [03-open](03-open.md) §1.
- **Правка `docs/process/flow.md`:**
  - после запуска нет остановок «Ч»;
  - отчёт Q3 в spec-PR;
  - бюджеты Q4;
  - исполнитель Q5;
  - ревью Q6;
  - v0 шире волны 1 ADR-0049: весь путь после запуска.
- **Backlog:**
  - цикл 1 (класс «контур доверия», merge бота на `MERGED`, код 4 / `retryable` из цикла 2 в 0.9.0);
  - триггеры: исполнитель B; gate ревью после attestation; пороги Q4 после 10 прогонов; одобрение spec review'ом для LOW после attestation (Q1 вариант B).
- **Временный узел человека:** до 0.9.0 impl-PR сливает maintainer (auto-merge кнопкой на GitHub). Условие удаления: вышел 0.9.0, и судья принимает merge бота на `MERGED`, где policy не требует `human-approval`.
- Кто пишет: классификатор auto-режима уже запрещал агенту записать ADR, расширяющий его полномочия («Instruction Poisoning», 2026-09-29). Агент пробует сам; при отказе даёт maintainer'у точные файлы, строки и текст.
