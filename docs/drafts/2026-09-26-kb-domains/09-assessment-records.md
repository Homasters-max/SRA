# Записи оценок и снимки: кэш как журнал для аудита

## Проблема

- Кэш хранит оценки Jev файлом на вопрос (`cache/q-<sha256>.json`: `q`, `scores {ключ заметки: оценка}`, `model`,
  `updated`); журнал вызовов (`usage.jsonl`) — топ-10 без ссылки на запись кэша. Связи «вопрос → оценки → выбранные
  units → `--used`» для аудита и анализа нет.
- При изменении заметки старая оценка удаляется из файла (перезапись) — история, на чём агент принял решение, теряется.
- Нет понятия «набор объектов, который оценивался»: нельзя сказать, устарела ли запись, и на каком составе корпуса она
  получена.
- Требование maintainer'а (2026-09-26): итоги Jev сохранять с ID, связанным с хэшем; запись — транзакция над группой
  объектов любого типа; изменение состава или тела объекта делает группу устаревшей, записи — помеченными устаревшими.

## Идея

Три сущности; записи неизменяемы (append-only), устаревание вычисляется — как `STALE` у evidence WARRANT (06a) и у
proposal LATTICE (01 §9).

| Сущность | Что это | Поля |
|---|---|---|
| **snapshot** (снимок; термин LATTICE, 01 §9) | неизменяемая группа объектов с версиями, над которой шла оценка: документы, units домена, объекты read model — любого типа | `id` = хэш отсортированных пар (`object_id`, `content_hash`); `created_at`; `source` (корпус / домен / context); `members[]` (`object_id`, `type`, `content_hash`); версии реестров (`registry_versions`, как у LATTICE) |
| **assessment** (запись оценки) | одна транзакция оценки: вопрос × snapshot × оценщик | `id` (ULID); `query_hash`; `q_norm`; `created_at`; `based_on` (snapshot `id`); оценщик: `model`, `prompt_hash`, `state_hash`, версия навыка; `scores {object_id: {score, content_hash}}`; `reused_from` (id записей, чьи оценки перенесены без вызова); `cost`, `tokens`, `ms`; `via` (cli, ui, bench, координатор), сессия / агент |
| **use** (след использования) | что с выдачей сделали | `assessment_id`; выдача (топ-N с итоговым баллом и причиной); выбранные units; `--used`; ответ «нет ответа» |

Ключ кэша (`query_hash` = хэш нормализованного вопроса + оценщик) находит **последнюю** запись; её статус вычисляется
сравнением `based_on` с текущим snapshot:
- `fresh` — состав и тела совпали: ответ без вызова Jev;
- `stale` — изменились отдельные объекты: новая запись, неизменённые оценки переносятся (`reused_from`), Jev
  оценивает только новое и изменённое (так кэш уже работает, но с перезаписью вместо новой записи);
- `superseded` — есть более новая запись на том же ключе.

Статус не пишется в запись (записи не мутируют); для скорости — вычисляемый индекс `key → последняя запись, статус`.

## Вопросы для grilling

1. Термин: `snapshot` (как LATTICE) для группы объектов и `assessment` для записи оценки? Рекомендация: да — один
   словарь с LATTICE; при подключении LATTICE его snapshot заменит наш.
2. Snapshot — на весь корпус / домен или только на объекты, реально оценённые в записи? Рекомендация: на оценённые
   (`members` = пул Jev): изменение чужого домена не старит запись.
3. Какие поля в ключе, какие — в записи? Рекомендация: ключ — `q_norm`, `model`, `prompt_hash`, `state_hash`; дата,
   версия навыка, snapshot, стоимость — поля записи (не ключа), иначе кэш не находит повтор.
4. «Тело объекта» для хэша: для unit — `title` + `summary` + `aliases` (то, что видит Jev) или ещё `refs`?
   Рекомендация: только то, что уходит в Jev; изменение `refs` не меняет оценку, но меняет «use» — отдельный хэш.
5. Хранилище: JSONL (append-only, как журналы) или файл на запись? Рекомендация: JSONL `assessments.jsonl` +
   `snapshots.jsonl` + индекс; порт хранилища (08) позволяет заменить.
6. Срок хранения и размер: записи растут на каждый новый вопрос и изменение корпуса. Рекомендация: хранить всё, что
   связано с `use` / `--used` / стендом; прочие `superseded` — сжимать через N дней.
7. Связь с журналами: `usage.jsonl` → `assessment_id`; `feedback.jsonl` и `runs.jsonl` стенда → `assessment_id`.
   Рекомендация: да — это и есть цепочка аудита «вопрос → оценки → выбор → польза».
8. Общий механизм для других мест (кэш Context Pack, классификации JEV, ответы агентов): snapshot + запись + вычисляемый
   статус — отдельный модуль 08 (`hash` + `cache` + `snapshot`)? Рекомендация: да; поиск — первый потребитель.

## Вне объёма

- Подпись записей и доверие к ним (attestation) — не нужно для локального инструмента разработки.
- Перенос истории в LATTICE — после его подключения (history window, 01 §8).
