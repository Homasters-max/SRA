## Context

После phase-3b (`v0.4.0`) набор тестов CLI — 686 тестов в 61 файле, из них около 250 в 20 e2e-файлах запускают
`node warrant.js` отдельным процессом во временном проекте. Каждый такой вызов порождает ещё процессы: `openspec` (Node-CLI,
старт около секунды) и `git`. Один e2e-тест стоит 1–15 с, файл — 30–60 с. На Windows порождение процессов в разы дороже:
job `test` на windows — 751 с против 346 с на ubuntu; `waive.test.ts` шёл 203 с в CI против 42 с локально, и vitest уронил job
на `Timeout calling "onTaskUpdate"`, хотя все файлы прошли. Локально полный `npm test` с параллелизмом по умолчанию даёт
таймауты, `/group-done` гоняет `--maxWorkers=3` вручную (долг «тесты под нагрузкой», NEXT-SESSION).

Факты кода (`packages/cli`, `v0.4.0`):

- Слой приложения уже есть: команды — `runX()` в `src/commands/*.ts`, возвращают `CommandResult`, не вызывают `exit`. Ни один тест
  их не вызывает — все идут через процесс.
- Все вызовы `openspec` проходят через один файл `core/openspec/cli.ts` (`runOpenspec`); вызовы `git` разбросаны по
  `core/ids/immutable.ts`, `core/gates/diff.ts`, `commands/classify.ts`; пользовательские команды check — `core/check/runner.ts`.
- `warrant validate` на репозитории идёт около 30 с: `checkPlacement` (`core/ids/scan.ts`) вызывает `openspec show` на каждый
  Change и spec; тот же путь идёт из `gate`, `verify`, `transition`. OpenSpec 1.13.1 не даёт пакетного `show`, а
  `validate --all --json` возвращает только `valid` и `issues` — «один вызов openspec на проект» невозможен.
- Подмена `openspec` в тестах — shim на `PATH` (`test/helpers/fake-openspec.ts`): процесс всё равно порождается, `list`/`show`
  не поддержаны.
- Подготовленный проект на файл уже есть (`useSyncedProject`: `beforeAll` + `cpSync` на тест), но `validate`, `sync`, `init`,
  `exit-criterion` делают `openspec init` в каждом тесте.

Второй довод — [ADR-0016](WARRANT-ADR-0016-mutation-diff-scope.md). Stryker мутирует `src`, а e2e запускают собранный `dist`:
мутанты для e2e невидимы, код, покрытый только e2e, даёт «выживших». Применить pack `bdd-tdd` к самому WARRANT (фаза 5) можно,
только если логика покрыта тестами без процесса. Третий — [ADR-0017](WARRANT-ADR-0017-check-execution.md): `tests-passed`
репозитория — это `npm test` под `timeout_s`, скорость набора — часть gate.

## Decision

1. **Четыре уровня; каталог = уровень.** `packages/cli/test/{unit,app,contract,e2e}/`, у каждого свой project в конфиге vitest.

   | Уровень | Что проверяет | Процессы |
   |---|---|---|
   | `unit` | функции `core/*`; файловая система во временном каталоге разрешена | запрещены |
   | `app` | команды `runX()` в процессе теста с фейковыми портами (п. 4) | запрещены |
   | `contract` | настоящие адаптеры портов против настоящих `openspec`, `git`, child process; соответствие фейков настоящим (п. 5) | разрешены |
   | `e2e` | бинарь `warrant`: argv, коды выхода, stdout/stderr, порождение процессов на платформе, golden, установка и состав пакета, сквозной lifecycle | разрешены |

   **Правило выбора уровня** (правило о решении): тест живёт на самом дешёвом уровне, который способен доказать проверяемое
   свойство. Отдельного уровня «vertical slice» нет — термин занят [13 §1](../13-roadmap.md); сквозной сценарий lifecycle — это
   один-два e2e-теста с причиной `lifecycle`.

2. **`Ctx`.** Команды и те функции `core`, которые прямо или транзитивно обращаются к порту, получают
   `Ctx { root, openspec, git, checks, clock, warn }` вместо `root`. Чистые функции получают данные, а не `ctx`. Production-`ctx`
   собирает `src/bin/warrant.ts` из адаптеров; неявного контекста (`AsyncLocalStorage`, глобальные сеттеры) нет. `runX()` и `Ctx` —
   **внутренний** API: внешний контракт вызова остаётся CLI (argv) — [ADR-0020](WARRANT-ADR-0020-warrant-sef-boundary.md) п. 11, D-21 (I5).

3. **Порты — узкие и смысловые, только используемые методы.** `OpenSpecPort` (`version`, `listChanges`, `listSpecs`, `showChange`,
   `showSpec`, `status`, `archive`, `newChange`, `schemaValidate`), `GitPort` (методы текущих вызовов: prefix, `HEAD`, дерево и
   содержимое на ревизии, изменённые пути от base), `CheckRunnerPort` (`run(command, {cwd, timeout}) → {exit, timed_out, output}`),
   `clock` (бывший параметр `today`). Разбор JSON и перевод ошибок — в адаптере. Метод добавляется вместе с командой, которой он
   нужен. Файловая система портом не становится.

4. **Фейки.** `FakeOpenSpec` ничего не разбирает: его модель (Changes, specs, requirements, scenarios с id, validity) заполняет
   `ProjectBuilder` одновременно с записью файлов. `archive` в фейке переносит Change в модели и фиксирует вызов; корректность
   слияния delta — ответственность OpenSpec. `FakeGit` — снимки деревьев `Map<rev, Map<path, content>>`, `HEAD`, prefix;
   `diffNames(base)` — разница снимков; снимок делает `ProjectBuilder.commit()`. Тест, которому нужен «битый» markdown или реакция
   настоящего парсера, по определению живёт в `contract` или `e2e`. Shim на `PATH` (`fake-openspec.ts`) удаляется; внедрение
   отказов переезжает в `app`.

5. **Контракт соответствия.** Для каждого порта `contract` содержит набор сценариев, который проходят и настоящий адаптер, и фейк:
   проект, собранный `ProjectBuilder`, даёт одинаковые ответы настоящего `openspec` и `FakeOpenSpec` по каждому методу порта;
   `GitCliAdapter` и `FakeGit` — одинаковые ответы на временном репозитории (в том числе prefix в подкаталоге и `HEAD` без коммитов).
   `contract` и `e2e` требуют `openspec` той версии, что зафиксирована в [ADR-0015](WARRANT-ADR-0015-openspec-sync-contract.md)
   (1.13.1): нет или другая версия — набор **падает** с понятным сообщением, не пропускается.

6. **`ProjectBuilder`** — helper уровня `app`: временный каталог, `ctx` с фейками, методы `withChange`, `withSpec`, `withRecord`,
   `withChecks`, `commit`, `synced` (последний вызывает `runSync` в процессе с тем же `ctx`). Методы появляются по мере переноса
   тестов. `useSyncedProject` (настоящие `openspec init` + `sync` один раз на файл, копия на тест) остаётся только в `e2e`.
   Общих мутируемых проектов нет.

7. **Проверки правила уровней** (правило о форме, ADR-0022 INV-04):
   - (a) в projects `unit` и `app` setup-файл делает `cross-spawn` и `node:child_process` бросающими `SPAWN_FORBIDDEN_AT_LEVEL` —
     ловится и транзитивное порождение;
   - (b) каждый e2e-файл начинается строкой `// e2e: <reason>`, reason ∈ `argv | exit-codes | output | platform-spawn | golden |
     package | lifecycle`; мета-тест проверяет наличие и значение;
   - (c) файл вне четырёх каталогов не входит ни в один project — мета-тест.

8. **Скрипты и CI.** `npm test` — все уровни; `test:unit`, `test:app`, `test:contract`, `test:e2e`, `test:fast` (= `unit` + `app`,
   для внутреннего цикла). Таймауты по project (`unit`/`app` — 5 с, `contract`/`e2e` — 60 с) и ограничение параллельности тяжёлых
   уровней — в конфиге, а не флагом вручную. CI: матрица ubuntu + windows, все уровни на каждом PR, у job `test` —
   `timeout-minutes`; ночных прогонов нет. Check `tests-passed` репозитория остаётся полным `npm test`; суженный прогон в gate не
   засчитывается (ADR-0017 п. 4).

9. **`validate` без N процессов подряд.** `checkPlacement` вызывает `show` только для Changes и specs, в файлах которых есть `REQ-` или
   `SCN-` (дешёвое чтение текста), и вызывает их асинхронно с ограниченным параллелизмом (как `--concurrency` OpenSpec). Кэш вывода
   `show` по хэшу содержимого и версии OpenSpec — только если замер после этого покажет `validate` репозитория дольше ~5 с.

## Consequences

- Поведение CLI не меняется; Change `test-levels` идёт с `skip_specs: true`, CLI `0.4.0 → 0.4.1` (R-14).
- Логика команд тестируется без процессов; e2e сокращаются до причин п. 7b (ориентир — 30–60 тестов вместо ~250; шаг тестов
  на Windows в CI — ≤ ~5 мин). Ориентиры — не gate: замер времени в CI нестабилен.
- ADR-0016 применяется к самому WARRANT в фазе 5: pack `bdd-tdd` на `packages/cli`, Stryker на diff. До этого код, покрытый только
  e2e, — долг, и это же критерий, какие e2e переносить.
- Любая новая команда фазы 4+ приходит с тестами `app` через `ctx`, а новый внешний вызов — с методом порта, адаптером, фейком и
  сценарием соответствия.
- Фейк может разойтись с OpenSpec при смене его версии: смена версии — ADR-0015, и контракт соответствия ловит расхождение до merge.
- Классификация уровней — только для самого WARRANT. Обобщение на проекты под WARRANT (`test_kind`, уровень `@SCN`-приёмочных
  тестов, [06 §6](../06-verification.md)) — долг фазы 5 вместе с pack `bdd-tdd` и spike S7.
- Долг «тесты под нагрузкой» и I-64 (`spawnSync` для `git` и `openspecAvailable()`) закрываются этим Change.

## Alternatives

- **Hexagonal / tactical DDD целиком** (Entity, Repository, FileSystemPort, контейнер зависимостей) — отвергнуто: файловая система
  во временном каталоге дешёвая; дорогое — только порождение процессов, порты нужны только там.
- **Неявный контекст** (`AsyncLocalStorage`) или глобальный сеттер портов — отвергнуто: зависимость не видна в сигнатуре, тест может
  незаметно уйти к настоящему `openspec`.
- **Сырой порт `run(args)`** — отвергнуто: фейку пришлось бы разбирать argv OpenSpec; контракт методов не проверить.
- **Фейк по записи и воспроизведению** вывода OpenSpec — отвергнуто: фикстуры устаревают молча, ключи по аргументам хрупкие.
- **Фейк, разбирающий markdown**, или **свой парсер** в `validate` — отвергнуто: второй парсер ядра (ADR-0001).
- **Импорт внутренних парсеров OpenSpec** по абсолютному пути — отвергнуто: не входят в `exports`, ломаются на любой версии.
- **Настоящий `git` на уровне `app`** — отвергнуто: исключение из правила «без процессов»; фейк со снимками достаточен, соответствие
  держит `contract`.
- **Поднять таймауты / число workers** — отвергнуто: лечит симптом; на Windows больше workers — больше конкуренции процессов и
  антивируса.
- **Уровень «vertical slice»** — отвергнуто: термин занят 13 §1; сквозной сценарий — e2e с причиной `lifecycle`.
- **`warrant test <level>`** — отвергнуто: ADR-0020 исключает раннер внутри WARRANT; уровни — npm-скрипты.
- **Разделение PR / nightly** — отвергнуто для MVP: после сокращения e2e все уровни укладываются в PR; nightly понадобится только
  для полного mutation (фаза 5).
- **Проценты пирамиды как цель или gate** — отвергнуто: правило уровня и проверки п. 7 держат форму, проценты — нет.
- **Пропуск `contract`/`e2e` без `openspec`** (`skipIf`) — отвергнуто: скрывает непроверенный контракт.
- **Перенос по частям в нескольких Change** — отвергнуто: проверка 7b сразу упадёт на непересмотренных e2e-файлах.
