# architecture-audit — метод

Подробный метод к навыку [architecture-audit](SKILL.md): что мерить, как метрика становится находкой, приоритет,
формат отчёта. Шаги навыка ссылаются на разделы ниже.

Аудит идёт поверх навыка [code-search](../code-search/SKILL.md): его шаги 1–6 действуют целиком (код — только
через `cs`, чтение — только диапазонами, код 2/3 не обходить, для разбора программой — `--json`). Здесь — метод: что
мерить, как метрика становится находкой, как ставится приоритет и куда уходит то, что не чинится сразу.

Когда: **перед spec-PR каждой фазы roadmap** (результат — вход в grilling нарезки; готовый запрос навыка `handoff`
начинается с аудита) и по запросу. Прошлые аудиты — [docs/process/audits/](../../../docs/process/audits/).

Инструменты:

- `cs map`, `cs deps`, `cs dups`, `cs callers`, `cs impact`, `cs skeleton`, `cs grep` — `node scripts/dev/cs.js <команда>`;
- `snapshot` — `node scripts/dev/arch-snapshot.js`: собирает ответы `cs --json` в снимок аудита и досчитывает то,
  чего в `cs` нет — сцепленность модулей, срезы по модулям с долей входного модуля, вызовы через порты в срезах
  (граф их не видит, [ADR-0029](../../../docs/adr/WARRANT-ADR-0029-graft-audit-dev-hooks.md)), разницу с прошлым
  снимком. `--dir` (по умолчанию `packages/cli/src`), `--level N` (глубина модуля, 2: `core/gates` ≠ `core/packs`),
  `--entries` (по умолчанию все `run<X>` в `<dir>/commands`), `--out`, `--against`, `--json`. ~20 с.

## Порядок

Шаги 1–4 собирают кандидатов, шаг 5 превращает кандидата в находку, 6–7 — оценка, 8 — куда она уходит. Кандидат без
шага 5 в отчёт не попадает.

### 0. Заявленная архитектура и прошлый аудит

Выпиши, что считается нормой: ADR про слои и порты (для CLI — ADR-0025: `commands/` — слой приложения, процессы
только в `adapters/`, порты в `core/ports/`), `docs/03-architecture.md`, мета-тесты раскладки (`test/unit/meta/`),
реестры и храповик архитектурного теста, когда они появятся. Правило, которое держится тестом, не перепроверяй —
отметь «держится». Отклонение от решения ADR — не находка, а вопрос к ADR.

Открой последний отчёт в `docs/process/audits/` и строки `A-N` в [`docs/backlog.md`](../../../docs/backlog.md): открытые
A-N перепроверяются, закрытые не должны вернуться.

### 1. Структура (количественно)

```bash
node scripts/dev/cs.js map
node scripts/dev/arch-snapshot.js --out docs/process/audits/<дата>.json --against docs/process/audits/<прошлый>.json
node scripts/dev/cs.js deps packages/cli/src --level 2 --cycles --runtime
node scripts/dev/cs.js dups --in packages/cli/src
git log --format= --name-only -- packages/cli/src | sort | uniq -c | sort -rn   # churn для приоритета
```

Разница со снимком прошлого аудита — первое, что смотреть: новый цикл, новое ребро «вверх», рост Ce или падение
cohesion модуля — кандидаты сами по себе. Кандидаты по порогам (пороги — отбор, не вердикт):

| Сигнал | Порог | Кандидат в |
|---|---|---|
| fan-in файла (`cs deps <файл>`, `importedBy`) | ≥ 15 и файл > 400 строк или в `skeleton` ≥ 3 несвязанных группы функций | god-объект |
| fan-in файла | ≥ 15, fan-out 0, файл маленький | **норма** (стабильный лист: ошибки, типы) — не находка |
| fan-out файла | ≥ 15 вне точки сборки (`bin/`) | оркестратор, раздутый вход |
| цикл файлов или модулей | любой | аномалия; только `import type` (нет в `--runtime`) — ниже приоритет |
| SDP | стабильный модуль (I < 0,3) зависит от нестабильного (I > 0,6) | нарушенная граница |
| cohesion модуля | < 0,2 при ≥ 3 файлах | «мешок» — или законный набор независимых частей (шаг 5) |
| `cs dups` | имя в ≥ 3 файлах | недостающая общая абстракция; `hazard` — ещё и граф теряет вызовы |
| рёбра «вверх» | `core/** → commands/**`, `adapters/** → commands/**`, `core → adapters` | нарушенная граница слоёв |

### 2. Вертикальные срезы

Входы — `runX()` в `commands/`. Снимок строит срезы всех входов; подробно разбирай сценарии, которые (а) меняют
состояние, (б) чаще правятся по `git log`, (в) затрагиваются ближайшей фазой (`docs/13-roadmap.md`). Один срез
целиком — `cs callers <вход> --direction out -d all --json`.

**Срез заканчивается на порту.** Граф не видит вызовов через порты (`ctx.git.head()` → адаптер): модуль `adapters`
в срезе по графу не появится никогда. Снимок дописывает к срезу вызовы портов (`ports`: `git.head×1`, …) — это связь
сценария с внешним миром; её рост между аудитами — отдельный сигнал.

Что искать:

- **общий ствол** — модули, которые есть в каждом срезе: настоящее ядро, его стабильность важнее всего;
- **доля входного слоя** (`entry_share`) > 0,15 — бизнес-логика в слое приложения;
- **похожие срезы** (одинаковый набор модулей, близкие числа) — прочитай входные функции диапазонами: общая
  последовательность шагов, скопированная между командами, — дублированная оркестрация;
- **неожиданный модуль** в срезе (транзакция ходит в `validate/`, статус — в `init/`) — функция лежит не там;
  найди её `cs impact <символ>`.

### 3. Инвентарь понятий (обязательно)

Импорты показывают только явную связь; скрытая — через понятия и форму данных. Список понятий берётся **из словаря**,
а не из головы аудитора:

1. Выпиши термины из `docs/02-vocabulary.md` — таблицы с термином в первой колонке и значения перечислений (оси
   статусов, `controller_action`, префиксы ID, уровни тестов) — плюс состояния и переходы из `docs/04-lifecycle.md`.
2. Для каждого перечисления — `cs grep '"<значение>"' --fixed` по 2–3 значениям: массив или `Set` с ≥ 2 значениями
   одного перечисления в двух и более местах — **размазанное понятие** (риск рассинхронизации). Одиночный литерал
   (`state !== "MERGED"`) — норма.
3. Для каждого понятия-сущности (gate, waiver, role, evidence, record, check…) — где его владелец: `cs grep` по имени
   файлов и функций; одно слово в файлах нескольких модулей (`waivers.ts` в `validate/` и `gates/`) — проверь, кто
   владелец; нет единственного — находка.
4. Связь через форму JSON: `cs grep 'json["' --fixed` и `cs dups` по guard'ам (`isPlainObject`) — сколько модулей
   читают нетипизированный JSON по строковым ключам.

`cs ask` — лексический поиск: для «где определено понятие X» он слаб; ищи по константе или литералу через `cs grep`.

### 4. Тесты — облегчённо

`packages/cli/test` — тоже архитектура (ADR-0025 задаёт уровни, фейки, `ProjectBuilder`). Только структура, без
срезов и инвентаря:

```bash
node scripts/dev/cs.js deps packages/cli/test --level 2
node scripts/dev/cs.js deps --cycles --in packages/cli/test
node scripts/dev/cs.js dups --in packages/cli/test
```

Кандидаты: хаб-помощник (`invoke`, `makeTempDir`, `useProjectBuilder`) с несвязанными обязанностями; копии фейков и
помощников между уровнями; тест уровня `unit`, импортирующий помощники `contract`/`e2e`.

### 5. Проверка кандидата → находка

Находка = метрика + код. Для каждого кандидата:

1. `cs skeleton <файл>` — сгруппируй функции по ответственности;
2. `cs impact <символ>` — кто на самом деле пользуется (включая вызовы, которых граф не видит); `callers` — только
   нижняя граница;
3. Read диапазона (1–2 функции) — подтверди, что смысл совпадает с метрикой;
4. цикл из одних `import type` — отметь (runtime его нет);
5. сверь с шагом 0: так решено в ADR — не находка (или находка к ADR, со ссылкой).

Не подтвердилось — выбрось, а не понижай приоритет.

### 6. Тип и приоритет

**Тип** — одно из: `coupling` (лишняя или неверно направленная связь между зонами), `cohesion` (зона делает
несвязанное или понятие размазано по зонам), `аномалия` (цикл, god-объект, нарушенная граница, копипаст — подтип в
скобках).

**Приоритет** — по трём осям, итог — по худшей:

| | P1 | P2 | P3 |
|---|---|---|---|
| Риск корректности | инвариант в ≥ 2 копиях (рассинхрон = неверное поведение) | — | — |
| Радиус | ≥ 3 срезов или fan-in ≥ 15 | 2 среза или fan-in 5–14 | 1 срез, локально |
| Ближайшая работа | фаза по roadmap добавит ещё одну копию / вход через это место | затронет | не затронет |

Churn (`git log`) — тай-брейк внутри уровня. Цена исправления на приоритет не влияет, пишется отдельно (S / M / L).

### 7. Гипотеза причины

Для каждой находки — одна проверяемая гипотеза, проверенная по git:

- **рост по группам/фазам**: копия появилась в коммите, где рядом уже был владелец (`git log --diff-filter=A`,
  `git log -S"<литерал>"`);
- **утилита там, где понадобилась впервые** (первый коммит функции и первый её вызыватель);
- **нет общей абстракции / типа** (`cs dups`, `json["`);
- **нет проверки направления зависимостей** (правило прозой или нигде; есть ли мета-тест);
- **осознанное решение** (ADR) — тогда это не находка.

### 8. Куда уходят находки

- Каждая находка получает ID **A-N** (сквозная нумерация между аудитами: следующий номер — после максимального в
  `backlog.md` и в прошлых отчётах) и строку в [`docs/backlog.md`](../../../docs/backlog.md): проблема и приоритет —
  «Что», change / фаза / долг — «Куда», аудит — «Источник».
- Взятая в работу — ссылка на A-N из tasks.md change'а; закрытая — строка удаляется (ADR-0032 п. 5).
- Не чинится сразу, а правило о ней проверяемо (ранги модулей, реестр помощников, реестр перечислений) — исключение
  с ID A-N в храповике архитектурного теста: новое нарушение роняет тест, ненужное исключение — тоже.
- Тип находки, которого проверка ещё не ловит, — кандидат в новое правило проверки (правило о форме без проверки не
  принимается, ADR-0022).

## Формат вывода

Отчёт — `docs/process/audits/<дата>.md` (по-русски) и снимок `docs/process/audits/<дата>.json` (`arch-snapshot/1`,
вывод `--out`). Разделы отчёта: 1. Область и заявленная архитектура; 2. Карта (модули из снимка, срезы, разница с
прошлым снимком); 3. Находки; 4. Что держится; 5. Воспроизведение (команды).

Находки — таблица, отсортированная по приоритету:

```text
| A-N | Проблема | Локация | Тип | Приоритет | Гипотеза | Исправление (цена) |
```

- **Локация** — `файл:Lx-Ly` из ответа `cs`, для модулей — каталог и рёбра-причины;
- **Проблема** — одно предложение с числом (fan-in, копий, срезов);
- после таблицы — по абзацу на P1/P2: доказательство (команда + что показала) и что сделать.

Качество самого графа (полнота, ложные рёбра) аудит не оценивает — это регрессия Graft
([graft.md](../../../docs/process/graft.md), `graph-audit.js`). Случай, где `cs` ошибся или промолчал и это повлияло
на находку, — отметить в отчёте и передать туда же.
