## Context

ADR-0009 п.4 требует, чтобы authoritative записи (переходы в `APPROVED`, `MERGED`; evidence для gates merge)
делал «CLI внутри CI», а запись `cli:local` для этих состояний считалась невалидной. Одновременно Change record
и evidence MUST коммититься ([04 §9](../04-lifecycle.md), [06a §5](../06a-evidence.md)). Следствие: CI должен
пушить коммиты в ветку PR или в `main`. Это создаёт известные проблемы: bot-коммиты в защищённый `main`,
сброс approval при пуше в ветку («dismiss stale reviews»), циклы CI, второй писатель одного файла.

Отдельная проблема — INV-03: если агент коммитит и открывает PR под аккаунтом человека, GitHub не даёт этому
человеку одобрить PR, а при solo-разработке второго человека нет.

## Decision

1. **CI никогда не пишет в репозиторий.** Любую запись в `.warrant/**` делает локальный CLI.
2. **Доверие — к ссылке, а не к писателю.** Переход в `APPROVED` / `MERGED` и evidence для gates merge валидны,
   только если несут верифицируемый `ref` (URL review, URL CI run, URL merge). CI проверяет ref через API форджа:
   существует, относится к нужному commit, approved, автор имеет роль, автор ≠ автор PR. Запись без
   верифицируемого ref — невалидна, кто бы её ни сделал.
3. **Правило вычисления gates в CI.** L0 / L1 CI считает только из evidence, произведённого в этом же запуске;
   закоммиченные L0 / L1 — черновики для локального controller, CI их игнорирует. Невоспроизводимое
   закоммиченное evidence (review, human approval) принимается только после верификации `attestation.ref`.
4. **Идентичность агента.** Агент работает под отдельной идентичностью форджа (GitHub App / bot). PR открывает бот,
   одобряет человек. `roles.*` в `warrant.json` не содержат ботов; `identities.agents` перечисляет ботов.
   Токен бота живёт только в окружении агента; `gh`-токен человека агенту недоступен.
5. **Форж.** MVP — GitHub.com + GitHub Actions. В CLI — интерфейс `forge` с единственной реализацией `github`.

## Consequences

- ADR-0009 п.4 уточнён: «authoritative запись = запись с верифицируемым ref», а не «запись, сделанная в CI».
  Правило [04 §9](../04-lifecycle.md) «`cli:local` невалиден для `APPROVED`/`MERGED`» заменено.
- Формат `ref` един: URL форджа (`https://github.com/<org>/<repo>/pull/12#pullrequestreview-…`,
  `…/actions/runs/8812`). Форма `ci:run/8812` и `ci://runs/8812` не используется.
- Транзиции record едут в *следующем* PR ([ADR-0011](WARRANT-ADR-0011-pr-topology.md)).
- PKI и подпись evidence не нужны в MVP; `signature` остаётся later.
- Retention CI-артефактов (90 дней) может стать failure mode для аудита. Тогда — orphan-ветка `warrant/state`,
  куда пишет CI; это upgrade по факту, не часть MVP.
- `warrant validate` отказывает, если в `.warrant/**` или `.claude/**` встречается строка, похожая на токен.

## Alternatives

- **CI пушит в ветку PR** — отвергнуто: сбрасывает approval, требует прав записи у CI, создаёт второго писателя.
- **CI пушит в orphan-ветку** — отложено: второй источник состояния (INV-06) без подтверждённого failure mode.
- **Approval через комментарий `/approve`** — отвергнуто: неотличим от комментария, который агент оставил через
  `gh` под токеном человека.
- **Второй человеческий аккаунт** — отвергнуто: не масштабируется на solo-разработку и ACP/API-агентов.
