## Context

Spike S2 ([13 §3](../13-roadmap.md)): [08 §8](../08-packs.md) требует, чтобы `openspec/config.yaml` и
`openspec/schemas/**` генерировались `warrant sync` из JSON, но не было проверено, что именно принимает
OpenSpec 1.13.1, как выглядит project-local schema и есть ли у OpenSpec собственные metadata Change,
которые стоит читать (остаток S3, [ADR-0009](WARRANT-ADR-0009-change-record-attestation.md)).

Факты получены командами `openspec init`, `openspec schema init | fork | validate | which`, `openspec new change`,
`openspec status | instructions | validate | show --json` и чтением `dist/core/project-config.js`,
`dist/core/change-metadata/schema.js`, `dist/core/artifact-graph/resolver.js` пакета 1.13.1:

Не трогает `.claude/settings.json` и `.claude/agents/` | Выходы `warrant sync` ([ADR-0014](WARRANT-ADR-0014-claude-code-enforcement.md)) и `openspec init` не пересекаются по файлам |

## Decision

1. **`warrant sync` генерирует в `openspec/` ровно три вещи** и ничего больше:
   - `openspec/config.yaml` — первая строка `# generated by warrant — do not edit`, затем ключи в фиксированном
     порядке `schema`, `context`, `rules`, `operations`. Другие ключи OpenSpec (`store`, `references`,
     `githubCopilot`) не генерируются: если они нужны проекту, это failure mode для нового ADR.
   - `openspec/schemas/<schema>/schema.yaml` — из `openspec/schema.json` pack'а (`warrant://openspec-schema/1`),
     тот же маркер первой строкой.
   - `openspec/schemas/<schema>/templates/**` — копии `openspec/templates/**` pack'а без изменений и без маркера
     (текст template попадает в artifacts агента; маркер там неуместен). Соответствие проверяется по hash в lock.
2. **Источники и слияние.** Pack поставляет `openspec/schema.json`, `openspec/rules.json`, `openspec/templates/`.
   Проект добавляет `.warrant/local/openspec/rules.json`. Слияние `rules.json`:
   `context` — конкатенация через пустую строку (pack, затем project); `rules.<artifact>` и
   `operations.<op>.guidance` — объединение списков с сохранением порядка (pack, затем project) и удалением
   точных дублей. Схема `warrant://openspec-rules/1` расширяется полем `operations` (`apply`, `archive`, каждое —
   `{ "guidance": string[] }`). В MVP schema поставляет только `core-sdd`; вклад других packs в artifact graph —
   later, по failure mode.
3. **Детерминированный YAML.** Генератор — собственный минимальный emitter: порядок ключей по схеме, отступ 2,
   LF, многострочные строки — literal block `|`, скаляры в двойных кавычках, если содержат `:`, `#`, ведущие
   пробелы или начинаются не с буквы. `warrant validate` сравнивает файлы **побайтно** с результатом генерации;
   расхождение — ошибка конфигурации (код 3).
4. **Schema `warrant-sdd` (core-sdd@0.1).** `name: warrant-sdd`, `version: 1`, четыре artifacts с графом
   `spec-driven`: `proposal` → `specs` (requires proposal) → `design` (requires proposal) → `tasks` (requires specs,
   design); `apply.requires: [tasks]`, `apply.tracks: tasks.md`. `instruction` каждого artifact — текст `spec-driven`
   плюс правила WARRANT (размещение `<!-- id: … -->`, `## Purpose` для новой capability, проекция
   `UNKNOWN` / `ASSUMPTION` по [02 §1](../02-vocabulary.md)); templates — по [13 §5](../13-roadmap.md)
   с сохранением раздела `## Capabilities` в proposal (контракт proposal → specs штатного workflow).
   Дополнительные artifacts (`waiver`, `experiment`) в graph не входят: это templates, а не узлы зависимостей.
5. **Что WARRANT читает у OpenSpec, а что нет.** Читает: `.openspec.yaml` → `schema`, `skip_specs`;
   `openspec status --json`, `openspec validate --strict --json`, `openspec show --json`, `openspec list --json`.
   Не читает как источник governance: `goal`, `affected_areas`, `initiative`. Не пишет: `.openspec.yaml`
   (только через `openspec new change`), `openspec/specs/**`, `openspec/changes/**`.
6. **Владение `.claude/`.** `.claude/commands/opsx/**` и `.claude/skills/openspec-*/**` принадлежат OpenSpec
   (`openspec init | update`); WARRANT их не генерирует, не проверяет и не включает в static deny — это
   инструкции, а не enforcement (INV-04). Строка добавляется в [03 §7](../03-architecture.md).
7. **Dogfooding фазы 1.** В этом репозитории OpenSpec инициализирован штатно (`--tools claude`, schema
   `spec-driven`), `config.yaml` ведётся вручную, пока `warrant sync` не существует. Переход на `warrant-sdd` —
   после фазы 2, отдельным `factory-change`.

## Consequences

- Spike S2 закрыт; остаток S3 закрыт (п. 5). Новая схема `warrant://openspec-schema/1`; `openspec-rules/1`
  получает `operations`. [08 §8](../08-packs.md) и [03 §7](../03-architecture.md) уточнены этим ADR.
- `ids-valid` и `warrant id` опираются на `openspec show --json`, а не на собственный парсер Markdown:
  формат spec принадлежит OpenSpec (ADR-0001).
- `warrant validate` получает три проверки, специфичные для OpenSpec: побайтное равенство сгенерированных файлов,
  `openspec schema validate`, ключи `rules` ⊆ artifacts schema.
- Языковая политика артефактов ([00](../00-readme.md)) реализуется строкой в `openspec-rules.context`, не флагом.

## Alternatives

- **Pack поставляет `schema.yaml` и `config.yaml` как YAML напрямую** — отвергнуто: нарушает ADR-0006
  (все файлы WARRANT — JSON с `$schema`), лишает `warrant validate` схемы для проверки и LLM — `description`.
- **Одна схема `openspec-rules/1` с вложенным `schema`** — отвергнуто: workflow schema и правила — разные объекты
  с разными владельцами (pack vs pack + project); «один объект — один файл».
- **Затенить пакетную `spec-driven` project-schema с тем же именем** — отвергнуто: `.openspec.yaml` фиксирует имя
  schema; смена содержимого под тем же именем ломает archive старых Changes незаметно.
- **Собственный парсер Markdown для ID** — отвергнуто: `show --json` уже отдаёт текст требований с ID первой строкой;
  второй парсер — второй источник истины о формате spec.
