# Архитектура поиска: модули, конвейер, порты

## Проблема

- Концепции поиска (кэш по хэшу, домены, units, ID-поиск, `--by-code`, порог «ответа нет», журналы, стенд) будут
  переиспользоваться в других местах SEF и в других проектах (maintainer, 2026-09-26): архитектура — модульная,
  гибкая и простая сразу.
- Сейчас навык `kb-search` — 5 файлов, 1141 строка; `kb-search.mjs` (389 строк) смешивает: Jev-клиент, кэш и ключ
  хэша, журналы, токенизатор и BM25, слияние, конвейер `search`, CLI, eval, обратную связь. Домены — отдельным
  `kb-domain.mjs`, но индекс выбирается ветвлением (`idxOf`), а ID-поиск и `--by-code` живут в CLI.
- Добавление шага (алиасы глоссария, read model LATTICE) сейчас — правка конвейера и CLI одновременно.

## Идея

Конвейер из независимых стадий над общим контрактом; каждая стадия — модуль с одной задачей; источники и внешние
сервисы — через порты. Конфигурация (`.kb-search.json`) задаёт состав и порядок стадий.

```
вопрос ─► normalize ─► [cache] ─► [id-lookup] ─► [alias] ─► scorers (bm25, jev) ─► fuse ─► threshold ─► выдача
                         │ hit        │ hit          │ boost          │                              │
                         └────────────┴──────────────┘                └──── журнал (usage) ◄─────────┘
```

| Модуль | Задача | Контракт |
|---|---|---|
| `normalize` + `hash` | нормализация вопроса, ключ `sha256(model, prompt, state, norm(q))` | чистые функции; переиспользуются вне поиска |
| `cache` | ответ по ключу; порт хранилища (файлы сейчас; другое — адаптер) | `get(key)`, `put(key, value)` |
| `source` | корпус: документы (md), домен (units), read model LATTICE — одинаковая форма «заметка» | `notes()`, `resolve(id)`, `sig` |
| `id-lookup` | детерминированный путь по ID нормы | `(q, source) → hits | none` |
| `alias` | термины и алиасы глоссария (курируемые + кандидаты) — буст, не замена | `(q, source) → boosts` |
| `scorer.bm25` / `scorer.jev` | оценки по заметкам; Jev — через порт `classifier` (сейчас Jev API) | `(q, notes) → {id: score}` |
| `fuse` | слияние оценок (`linear`, `rrf`) | `(scores[]) → scores` |
| `threshold` | «ответа нет» по уверенности | `(scores) → ok | no-answer` |
| `log` | журналы JSONL: usage, feedback, runs | `append(kind, row)` |
| `bench` | стенд: наборы, метрики, бутстрэп, `runs.jsonl` | поверх `search(q, config)` |
| `cli` / `ui` | только разбор аргументов и вывод | вызывают `search`, `refs`, `byCode` |

Правила: стадия не знает о соседях (только общий контракт «вопрос → кандидаты с оценками и причиной»); внешние
сервисы — только через порт (Jev, хранилище, LATTICE); ничего проектного в ядре (пути, домены, промпты — в
конфигурации проекта).

## Вопросы для grilling

1. Где живёт ядро: навык (общий для проектов) или пакет в репозитории SEF? Рекомендация: пока навык, с разделением
   файлов по модулям; пакет — когда появится второй потребитель вне Claude Code.
2. Контракт стадии: `(ctx) → ctx` с полями `q`, `candidates`, `scores`, `trace` (почему найдено)? Рекомендация: да —
   `trace` нужен и для журнала, и для объяснения выдачи агенту.
3. Порт `classifier` — только Jev или общий (другая модель оценки)? Рекомендация: общий интерфейс `score(q, items,
   state)`; Jev — первый адаптер.
4. Порт `source` для LATTICE — сразу читать `sef://lattice-read-model/1` (02-entity-model)? Рекомендация: адаптер
   появляется вместе с LATTICE; до того — локальные файлы той же формы.
5. Кэш: ключ включает версию источника (`sig`) или только вопрос и промпт? Рекомендация: вопрос + модель + промпт +
   `state`; оценки — по ключу заметки (уже так), поэтому смена корпуса дооценивает только новое.
6. Порядок рефакторинга: сначала разнести `kb-search.mjs` на модули без изменения поведения (стенд — регрессия),
   затем новые стадии? Рекомендация: да; критерий — те же метрики на регрессионном наборе.
