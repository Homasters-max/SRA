# WARRANT flow — конвейер Change, основа тёмной фабрики

Источник: аудит 2026-09-29, `80-flow-dark-factory.md` (перенесён, дальше правится здесь). Факты — на HEAD `b578861`.

## Проблема

Человек стоит на каждом шаге доставки Change: план, три «merge #N» синхронно в чате, активации waiver. Замер PR #67…#100 — `70-fast-mode-git-speed.md` аудита. Агент и maintainer — один аккаунт GitHub (WS-04), поэтому решение человека нельзя выразить review «Approve», а след автоматических merge приписывается человеку. Судья не закрывает WS-03, WS-13, WS-14 — автоматизация без их исправления пропустит дыры.

Разбор предложения «убирать шаги, а не ускорять их» (2026-09-29). Я принимаю, дорабатываю или опровергаю идеи, затем даю минимальный целевой дизайн и порядок внедрения, при котором ускорение начинается раньше всего.

Опора:
- замер PR #67…#100 (`70-fast-mode-git-speed.md`);
- навыки `git-start`, `git-land`, `change-spec-pr`, `change-impl-pr`, `change-archive-pr`, `fast-mode`;
- контроллер `packs/core-sdd/controller/rules.json`;
- реестр аудита WS-01…30;
- база kb: TERM-073 Dark software factory, ANT-032 Builder self-validation, TERM-195 Independent verification, TERM-173 Risk-scoped autonomy, PAT-108 Risk-calibrated review, PAT-097 Recoverable runs, PAT-006 Reconcile loop, TERM-035 Theory of Constraints.

## Идея

### 1. Вердикт по идеям
| # | Идея | Вердикт | Почему, и что меняю |
|---|---|---|---|
| 1 | Цель — убирать шаги, не требующие решения человека, а не ускорять их | ✅ Принять как главный принцип | Совпадает с определением тёмной фабрики (TERM-073): «темнота» — это отсутствие рутинного труда, а не отсутствие governance. Добавляю из того же определения: **надо назвать, какой именно цикл тёмный**. У нас это цикл доставки Change. Написание spec и кода и проверку это пока не затрагивает |
| 2 | Change — одна управляемая единица, PR — транспорт | ✅ Принять | Человек и агент думают «продвинуть Change». PR, ветки и worktree не видны |
| 3 | `warrant change start/land` — **внутри CLI WARRANT** | ❌ Опровергнуть место, принять смысл | Судья и исполнитель не должны быть одним компонентом. Исполнитель, который сам пушит, сливает и судит, — это ANT-032 (самоотчёт исполнителя как гейт); нужна независимая проверка (TERM-195). К тому же CLI по устройству пассивен, а CI ничего не коммитит (ADR-0010 п. 1). **Поэтому flow — отдельный тонкий инструмент над публичным CLI** (`warrant … --json`), `git` и `gh`. Бонус: flow становится **первым потребителем контракта CLI** внутри SRA. Каждая его нужда разобрать внутренности — сигнал пробела контракта (WS-05) |
| 4 | Не строить orchestrator, event bus, DSL, новую state machine | ✅ Принять и усилить | **Flow без собственного состояния.** Стадия каждый раз выводится из наблюдаемого: `warrant status` (состояние Change, `controller_action`), `git` (ветка, worktree, чистота) и `gh` (PR, проверки, review, merge). Это reconcile «наблюдай → сделай один шаг» (PAT-006) без движка. Повтор после любого обрыва продолжает с того же места (PAT-097). Таблица стадий — чистая функция на ~10 строк (§3), а не state machine |
| 5 | Четыре команды: start / land / status / finish | ⚠️ Три | `finish` не нужен. `land` после merge сам делает чистку и переход к следующей стадии, потому что идемпотентен. Остаются `start`, `land`, `status` (`status` заодно служит входящими решений человека) |
| 6 | «Человек решает, что Change готов к следующей стадии» | ❌ Опровергнуть | Для тёмной фабрики готовность решают **gates**, а не человек. Человек решает только то, что policy WARRANT помечает как человеческое: намерение, одобрение spec при заданном риске, приёмку результата при `human-approval`, waiver, блокирующий UNKNOWN. Точки решений **выводятся из действующей policy по риску** (TERM-173, PAT-108), отдельного конфига нет. Merge archive-PR — механика и никогда не решение (§4) |
| 7 | 3 → 2 → 1 PR «не меняя процесса» | ⚠️ Частично | Flow делает число PR невидимым, это верно. Но три PR — не транспорт, а модель доверия судьи: policy из базы (ADR-0038) и evidence на merge-коммите M. Сократить их — решение нормы WARRANT (ADR), а не flow. **Сейчас оставить 3.** Archive-PR сделать полностью автоматическим, тогда его человеческая цена — 0 |
| 8 | Главный KPI — простой человека, а не время CI | ✅ Принять и уточнить | Простой снижают не давлением на человека, а тем, что **решения асинхронны и собраны в одну очередь**. Решение — review «Approve» на GitHub, с телефона, в любое время; flow его подхватывает. Для этого нужна идентичность агента (п. 10) |
| 9 | Обход → дефект → исправление CLI → удалить обход | ✅ Принять | Это стабилизация, а не оптимизация. Каждый обход в навыке помечается ссылкой на строку бэклога, счётчик обходов → 0 (§7) |
| 10 | GitHub App — «второй уровень, не prerequisite» | ❌ Опровергнуть для тёмного режима, принять для App | Нужна не App, а **машинный пользователь** — второй GitHub-аккаунт агента с fine-grained PAT, около 30 минут настройки. Он **нужен сразу**, по трём причинам:<br>1. GitHub не даёт автору одобрить свой PR. При общем аккаунте maintainer не может поставить «Approve» на PR агента, поэтому решения идут словами в чате («merge #N»), синхронно и без следа.<br>2. Каждый автоматический merge под общим аккаунтом записывается как акт maintainer'а. След фабрики лжёт (WS-04).<br>3. С машинным аккаунтом решение человека становится review «Approve» — асинхронным, атрибутированным и проверяемым судьёй (ссылка `#pullrequestreview-<id>` уже поддерживается для UNKNOWN).<br>App — позже, для archive-PR и тега workflow'ом (ADR-0047 п. 3) |
| 11 | Не трогать merge queue, runners, распределённость, агрессивную параллелизацию, массовый переход на 1 PR | ✅ Принять | Merge queue для репозитория на личном аккаунте, скорее всего, недоступен; `strict: false` + детектор на push в `main` дешевле |
| 12 | Автоматизация «скучная»: скрипты + CLI + gh | ✅ Принять | Три слоя, четвёртого не нужно. Уточнение: слой «WARRANT flow» ≠ WARRANT CLI (п. 3) |
| 13 | LATTICE — первый потребитель flow | ✅ Принять, но после SRA | Flow сначала обкатать на SRA (dogfooding), затем поставить потребителю. Жёстко прошитых путей SRA нет: имена проверок, пути, роли берутся из `warrant.json` и `gh` |

**Чего не хватает в предложении.** Автоматизация усиливает и честность, и дыры. Сейчас дыры в вердикт закрывает человек на каждом merge. Убрать его без исправления судьи — значит пропускать через конвейер то, что судья не проверяет:
- WS-03: судья проверяет у `MERGED` только gates со значением `PASS`;
- WS-13: `.claude/**` не входит в policy-пути, агент может снять себе guard;
- WS-14: PR без Change с `src/**` проходит.

Ещё две предпосылки автоматизации:
- **Сбой нужно отличать от отказа** (WS-06, код 4 / `retryable`), иначе flow не знает, повторять или останавливаться.
- **Флейк BL-89 нужно убрать**, иначе конвейер будет вставать каждый день.

### 2. Целевой дизайн — минимальный
```text
┌───────────────────────────────┐
│ Человек: намерение, одобрения  │ ← review «Approve» на GitHub, асинхронно
│ Агент: spec, код, review spec  │ ← смысловая работа
└──────────────┬────────────────┘
               ▼
┌───────────────────────────────┐
│ flow: start · land · status    │ ← скрипт, без своего состояния
│ таблица стадий = f(наблюдаемое)│
└──────────────┬────────────────┘
               ▼
┌───────────────────────────────┐
│ warrant (судья, пассивен)      │
│ git · gh · CI (reusable wf)    │
└───────────────────────────────┘
```

**Принципы flow (6 правил):**
1. **Нет своего состояния.** Стадия — из `warrant status --json`, `git` и `gh`. Ни одного файла состояния flow.
2. **Идемпотентность.** Любую команду можно повторить: PR уже есть — не создаёт; слит — чистит; ветка удалена — пропускает.
3. **Один вызов — до первой остановки.** Останавливается только на: смысловой работе агента, решении человека, красном CI по правилу, неизвестной ситуации.
4. **Только публичный контракт CLI.** Flow не читает `.warrant/**` напрямую. Нужда в этом — строка бэклога «пробел контракта».
5. **Детерминированный текст.** Сообщения коммитов и тела PR — из шаблона и артефактов Change (`proposal.md`, `tasks.md`, вывод `verify`), без LLM. Каждый коммит flow несёт трейлер `Flow: <stage>`.
6. **Не решает за человека и не обходит защиту.** Нет `--admin`, нет правки защиты, нет активации waiver без ссылки на решение.

**Команды:**
- `flow start <change|task>` — worktree + ветка от `origin/main`: переиспользует свободный worktree, `fetch --prune`. Для Change выбирает ветку по стадии.
- `flow land [<change>]` — проводит Change до следующей остановки. Для не-Change работы (`docs`/`process`/`fix`) — commit → PR → `--auto` → чистка. **Отказывается** выпускать не-Change PR с путями `paths.src`/`paths.tests`, пока WS-14 не закрыт у судьи.
- `flow status` — все Change и ветки одной таблицей: стадия, что делает машина, **чего ждут от человека** (ссылка на PR и одно действие). Это и есть «входящие решений».

### 3. Таблица стадий (чистая функция наблюдаемого)
Собрана из шагов навыков `change-*-pr`. **М** — механика, flow делает сам. **А** — остановка на работу агента. **Ч** — остановка на решение человека.

| Наблюдаемое | Действие flow | Кто |
|---|---|---|
| `PROPOSED`, артефакты не закоммичены или не валидны | `openspec validate --strict`, коммит | М; ошибка валидации → А |
| `PROPOSED`, нет review spec | стоп: «review — субагент `warrant-reviewer`, `run start … --operation review`» | А |
| `PROPOSED`, review `BLOCKER` | стоп: «правка spec» | А |
| `PROPOSED`, review `PROVEN` | `classify` (профиль по floor, п. 5.3), `verify`, PR spec, `--auto` не ставить, если одобрение spec за человеком | М |
| spec-PR открыт, одобрение за человеком, review «Approve» нет | стоп в `status`: «одобрить spec-PR #N» | Ч |
| spec-PR одобрен (review maintainer'а) | активация waivers `--ref <review>`, `verify`, `transition SPECIFIED`, push, `--auto` | М |
| spec-PR слит, Change `SPECIFIED` | ветка impl, `transition APPROVED --ref`, `IMPLEMENTING`, коммит | М |
| `IMPLEMENTING`, группы `tasks.md` не закрыты | стоп: «реализация, группа N» | А |
| `IMPLEMENTING`, все группы закрыты | `verify`, `transition VERIFYING`, PR impl; `--auto`, если на `MERGED` нет `human-approval` | М |
| impl-PR зелёный, на `MERGED` есть `human-approval`, «Approve» нет | стоп: «принять impl-PR #N» | Ч |
| impl-PR слит | ветка archive, `ci fetch`, `transition MERGED --ref`, `archive`, PR, `--auto` | М |
| archive-PR слит | чистка worktree и веток, `pull --ff-only`; тег — workflow (ADR-0047 п. 4) | М |
| CI красный: инфраструктура (код 4 / `retryable`) или известный флейк | 1 повтор, затем стоп | М → стоп |
| CI красный по правилу | стоп: сводка находок | А |
| конфликт версий (`package*.json`, lock, golden) | рецепт ADR-0047 п. 6: `--theirs`, bump, `sync`, `golden:update`, `check.js` | М |
| любой другой конфликт или непредусмотренная комбинация | стоп: «не знаю — вот наблюдаемое» | А |

### 4. Точки решения человека — из policy, по риску
| Решение | LOW | HIGH | Форма |
|---|---|---|---|
| Намерение и план (что делаем, границы) | да | да | одно сообщение в начале задачи |
| Одобрение spec | **нет** (review-субагент независим, `PROVEN` без MAJOR) — решение Р-F1 | да | GitHub review «Approve» на spec-PR |
| Приёмка impl | нет (gates) | да, если в policy есть `human-approval` на `MERGED` | GitHub review «Approve» на impl-PR |
| Waiver, блокирующий UNKNOWN | да | да | комментарий или review в PR (уже проверяемо, R-29) |
| Merge archive-PR, docs/process-PR | **никогда** | **никогда** | — |

**Человеческих действий на Change:**
- сейчас: план + 3 × «merge #N» + активации waiver, синхронно в чате;
- цель для LOW: **1**;
- цель для HIGH: **2–3**, асинхронно, с телефона.

### 5. Порядок внедрения — раньше ускорение, потом «темнота»
#### Волна 0 — сегодня, без кода (минуты)

1. `delete_branch_on_merge: true` в настройках репозитория.
2. Правило (строка в ADR-0047 или новый ADR):
   - ADR, объявляющий Change, — в spec-PR;
   - `docs`/`process`-правки сессии — одним PR;
   - строки бэклога — с Change;
   - **merge archive-PR — не решение человека**.
3. Машинный пользователь агента:
   - второй аккаунт, collaborator с `write`;
   - fine-grained PAT в `GH_TOKEN` среды агента;
   - в `warrant.json` у SRA и LATTICE — `identities.agents: ["<бот>"]`.

   Сразу даёт асинхронные «Approve» и честную атрибуцию.

#### Волна 1 — 1–2 дня: `scripts/dev/flow.js` v0 (самая дешёвая и самая частая механика)

1. `start`, `status`, `land` — для **не-Change PR** (половина всех PR) и **стадии archive** (100 % механики).
2. Тесты: таблица стадий — unit на наблюдаемом (fake gh/git уже есть). Повтор после обрыва на каждом шаге.
3. Лёгкий CI для `docs`-only diff: обязательные job'ы стартуют и выходят зелёными шагом-фильтром.

**Готово, когда:** docs-PR и archive-PR проходят одной командой `flow land`, ноль ручных git-команд.

#### Волна 2 — 2–4 дня: убрать обходы (стабилизация, параллельно с волной 1)

- ISS-018: spec-report привязать к `spec_tree`. Исчезает «`verify` перед `APPROVED`».
- `transition` при отказе gate ничего не пишет. Исчезает «откатить `human-approval`».
- `verify --dry-run`, или проверки только через `check.js`. Исчезает «откатить manifest и EVID».
- Коды выхода: код 4 и `retryable` (WS-06).
- BL-89: `tests-passed` не пересобирает глобальный `warrant` (tgz), `build.js` чистит `dist`.
- WS-01/02: установка из тега и канарейка — нужна, чтобы flow работал у LATTICE.

**Готово, когда:** в навыках 0 строк-обходов.

#### Волна 3 — flow на всех стадиях + предпосылки «темноты»

1. Стадии spec и impl в `flow land` по таблице §3; review-решения — из GitHub review бота и maintainer'а.
2. Судья:
   - WS-03 — сверка всей записи, `WAIVED`/`NOT_APPLICABLE` с файлами waiver;
   - WS-13 — `.claude/**` в policy-пути, `validate` в reusable workflow;
   - WS-14 — PR без Change с кодом → нарушение;
   - акт человека ∉ `identities.agents` (WS-04).
3. Детектор на push в `main` (прогон тестов), вместо `strict` (WS-16).

**Готово, когда:** LOW-Change от плана до тега проходит с одним действием человека.

#### Волна 4 — поставка и пилот

1. Flow в продукт: скрипт и навык в pack `core-sdd`, **отдельно от кода судьи**. Настройки — из `warrant.json`.
2. Пилот на LATTICE: следующий Change полностью через flow. Метрики §7 до и после.

### 6. Навык после волны 3 (черновик `fast-mode`, ~10 строк)
```text
1. План: цель, границы, риск, 1–3 вопроса. Ответ человека = намерение.
2. `flow start <change>`.
3. Смысловая работа по остановке flow: spec → review-субагент → код по группам.
4. `flow land`. Остановка «А» — исправить по сути и снова `flow land`;
   «Ч» — сообщить человеку одну строку из `flow status` и взять следующую задачу.
5. Стоп: тот же красный CI после двух исправлений; решение, меняющее spec/ADR, — вопрос человеку.
```

`git-start`, `git-land` и механические шаги `change-*-pr` исчезают из навыков. Остаётся смысловое: review spec, реализация групп, решения I-N.

### 7. Метрики без нового состояния
| Метрика | Как считать | Цель |
|---|---|---|
| **Человеческие действия на Change** (главная) | Review и комментарии maintainer'а в PR Change + ручные коммиты без трейлера `Flow:` | LOW 1, HIGH 2–3 |
| **Простой человека на Change** | Сумма «стоп Ч → review maintainer'а» по времени событий `gh` | Падает от волны к волне |
| Lead time Change | Первый коммит spec → тег или merge archive | — |
| **Счётчик обходов** | Строки навыков с пометкой `<!-- workaround: BL-N -->`; lint `dev-context.test.ts` запрещает обход без ссылки | 0 |
| Ручные git-команды | Коммиты без трейлера `Flow:` на ветках Change | ≈ 0 для механики |
| PR на Change, доля docs-PR | `gh pr list` | 3; доля падает |
| Повторы и остановки flow по типам | Трейлеры и тела PR | Инфраструктура → 0 после BL-89 |

### Итог
Идея верна, и её главный принцип я принимаю: **человек управляет смыслом, система — механикой**. Для тёмной фабрики её нужно дополнить тремя вещами:
1. **Flow отделён от судьи** и опирается только на публичный контракт.
2. **Решения человека выводятся из policy по риску** и принимаются асинхронно, как GitHub review. Для этого идентичность агента нужна сразу, а не «потом».
3. **Человека из цикла можно убирать только после того, как судья закрывает WS-03, WS-13 и WS-14.** Иначе конвейер автоматизирует и дыры.

Первое ускорение даст волна 0 (минуты) и волна 1 (1–2 дня): половина PR и вся стадия archive уходят в одну команду.

## Вне объёма
